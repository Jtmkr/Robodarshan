Serial: talking to your computer

A robot that does something wrong cannot tell you why, so the first thing you need is a way to make it talk. Serial is the simplest one: the ESP32 sends text over the USB cable and the Serial Monitor in the Arduino IDE shows it on your screen. You will use it in almost every lesson in Stage 2 to print sensor values, check which branch of your code ran, and tune your robot.

void setup() {
  Serial.begin(115200);              // start serial at 115200 baud
  Serial.println("Robot booting...");
}

void loop() {
  int sensor = analogRead(34);       // ESP32 ADC gives 0 to 4095
  Serial.print("sensor = ");
  Serial.println(sensor);
  delay(200);
}

Open Tools → Serial Monitor and set the speed box at the bottom to 115200. It must match the number in Serial.begin().

Serial.print()

Prints a value and stays on the same line.

Serial.println()

Prints a value and moves to the next line.

Serial.available()

Returns how many characters are waiting for you to read.

Serial.read()

Reads one waiting character.

Random symbols in the Serial Monitor?

The speed in the Serial Monitor does not match Serial.begin(). Fix the number and the text will be readable again. Printing very fast also slows your robot down, so remove or reduce prints once your robot works.

UART: two devices, two wires

UART (Universal Asynchronous Receiver/Transmitter) is the protocol behind Serial. Each side has a TX pin that transmits and an RX pin that receives. There is no shared clock, so both sides must agree on the baud rate (bits per second) in advance, for example 9600 or 115200.

  • Cross the wires: my TX goes to your RX, and my RX goes to your TX.
  • Share the ground between the two devices.
  • Data is sent as frames: a start bit, 8 data bits and a stop bit. This common format is written 8N1 (8 data bits, No parity, 1 stop bit).
  • The ESP32 logic level is 3.3 V. Do not connect a 5 V TX pin directly to an ESP32 RX pin.

The ESP32 has three UART ports. Serial (UART0) is used by the USB cable, so use Serial2 for your own devices. Its default pins are GPIO16 (RX2) and GPIO17 (TX2).

#define RX2 16
#define TX2 17

void setup() {
  Serial.begin(115200);                              // to the computer
  Serial2.begin(9600, SERIAL_8N1, RX2, TX2);         // to the other device
}

void loop() {
  if (Serial2.available()) {                         // data from the device
    char c = Serial2.read();
    Serial.print("Received: ");
    Serial.println(c);
  }
  if (Serial.available()) {                          // data typed on the computer
    Serial2.write(Serial.read());                    // forward it to the device
  }
}

Connect two ESP32 boards (or an ESP32 and a Bluetooth module) like this and whatever you type on one side appears on the other.

Using an ESP32-WROVER?

On WROVER modules GPIO16 and GPIO17 are used internally for extra memory (PSRAM). Pick other pins in Serial2.begin(); the ESP32 lets you choose almost any free pins for a UART.

I²C: many devices on two wires

I²C (Inter-Integrated Circuit) connects one controller to many small chips such as gyroscope sensors, OLED displays and ADC chips, using just two wires:

  • SDA: the data line.
  • SCL: the clock line, generated by the controller.

Every device has a 7-bit address, and the controller starts each message by saying whose address it is talking to. Only that device answers. Common addresses are 0x68 for the MPU6050 gyroscope/accelerometer, 0x3C for small SSD1306 OLED displays and 0x48 for ADS1115 ADC chips.

  • ESP32 default pins: SDA = GPIO21, SCL = GPIO22. You can change them in Wire.begin(sda, scl).
  • Both lines need pull-up resistors to 3.3 V (usually 4.7 kΩ). Most sensor breakout boards already have them.
  • Speed is usually 100 kHz (standard) or 400 kHz (fast), set with Wire.setClock(400000).

When a new I²C device does not work, the first question is always “does the ESP32 even see it?” This scanner answers that:

#include <Wire.h>

void setup() {
  Serial.begin(115200);
  Wire.begin(21, 22);                    // SDA, SCL
  Serial.println("Scanning I2C bus...");
}

void loop() {
  byte found = 0;
  for (byte address = 1; address < 127; address++) {
    Wire.beginTransmission(address);
    if (Wire.endTransmission() == 0) {   // 0 means a device answered
      Serial.print("Device found at 0x");
      Serial.println(address, HEX);
      found++;
    }
  }
  if (found == 0) Serial.println("No devices found. Check wiring and pull-ups.");
  delay(3000);
}
Why this matters for your line follower

The QTR-8A sensor array has 8 analog outputs, but the ESP32 has only a handful of analog pins that work reliably. An I²C ADC chip such as the ADS1115 (4 channels per chip, so two chips for 8) is one way to read all eight. You will meet this again in the sensors lesson.

SPI: fast, with a wire per device

SPI (Serial Peripheral Interface) is built for speed. It is used for SD cards, fast displays and some sensors. It uses four signals:

  • SCK: the clock, from the controller.
  • MOSI (Master Out, Slave In): data from the ESP32 to the device.
  • MISO (Master In, Slave Out): data from the device to the ESP32.
  • CS (Chip Select, also called SS): pulled LOW to say “I am talking to you now”. Each device has its own CS wire.

On the ESP32 the default SPI pins (called VSPI) are SCK = 18, MISO = 19, MOSI = 23, CS = 5. SPI sends and receives at the same time: every byte you send also returns a byte.

#include <SPI.h>

const int CS_PIN = 5;

void setup() {
  pinMode(CS_PIN, OUTPUT);
  digitalWrite(CS_PIN, HIGH);            // HIGH = device not selected
  SPI.begin();                           // uses the default VSPI pins
}

byte transferByte(byte out) {
  SPI.beginTransaction(SPISettings(1000000, MSBFIRST, SPI_MODE0));  // 1 MHz
  digitalWrite(CS_PIN, LOW);             // select the device
  byte in = SPI.transfer(out);           // send one byte, receive one byte
  digitalWrite(CS_PIN, HIGH);            // deselect
  SPI.endTransaction();
  return in;
}

The mode (SPI_MODE0 to SPI_MODE3) and bit order come from the device's datasheet. If a device returns garbage, check the mode first.

Rule of thumb

Use the protocol the chip is built for. Prefer I²C when you have many slow sensors and few pins, SPI when you need speed, and UART for point-to-point links like Bluetooth modules.

Wi-Fi: putting the ESP32 on a network

Wi-Fi is the reason ESP32 boards are popular in robotics: it lets your robot be controlled from a phone or send data to a computer without extra modules. The ESP32 supports two modes:

  • Station (STA): the ESP32 joins an existing network, like a phone does.
  • Access point (AP): the ESP32 creates its own network that your phone joins. No router needed, which is ideal at competitions.
#include <WiFi.h>

const char* WIFI_SSID = "YourNetwork";
const char* WIFI_PASS = "YourPassword";

void setup() {
  Serial.begin(115200);
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);

  Serial.print("Connecting");
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.println();
  Serial.print("IP address: ");
  Serial.println(WiFi.localIP());        // note this down, you will need it
}

void loop() {}

To create your own network instead, use access point mode. The password must be at least 8 characters, and the ESP32's address is 192.168.4.1 by default:

WiFi.mode(WIFI_AP);
WiFi.softAP("Robodarshan-Bot", "robot1234");
Serial.println(WiFi.softAPIP());         // 192.168.4.1
Things that catch beginners
  • The classic ESP32 supports 2.4 GHz only. It cannot join a 5 GHz-only network.
  • Networks that need a login page (many campus and hostel networks) will not work in station mode. Use your phone's hotspot or access point mode.
  • While Wi-Fi is on, the pins that belong to the ESP32's ADC2 cannot be read with analogRead(). Use ADC1 pins (GPIO32 to 39) for sensors.

Web server: a control page on your robot

A web server waits for a browser to ask for a page and replies. Your ESP32 can do this too: type its IP address in a phone browser, the ESP32 receives the request and sends back a page. Each address path, like / or /forward, is called a route, and you decide what your code does for each route.

#include <WiFi.h>
#include <WebServer.h>

WebServer server(80);                    // port 80 is the normal web port

void handleRoot() {
  server.send(200, "text/html", "<h1>Hello from the ESP32</h1>");
}

void handleLed() {
  digitalWrite(2, !digitalRead(2));      // toggle the on-board LED
  server.send(200, "text/plain", "OK");
}

void setup() {
  pinMode(2, OUTPUT);
  WiFi.mode(WIFI_AP);
  WiFi.softAP("Robodarshan-Bot", "robot1234");

  server.on("/", handleRoot);            // route for the page
  server.on("/led", handleLed);          // route for an action
  server.begin();
}

void loop() {
  server.handleClient();                 // must run often
}
  • 200 is the HTTP code for “OK”; 404 means “not found”.
  • server.handleClient() has to be called again and again. If your loop() contains long delay() calls, the page will feel dead. The next lesson shows how to avoid this with millis().

Bluetooth and BLE

The ESP32 supports two kinds of Bluetooth:

Classic Bluetooth

Behaves like a wireless serial cable (SPP). Simple to use, works with Android serial terminal apps. Only on the classic ESP32, and iPhones cannot use it.

BLE (Bluetooth Low Energy)

Low power, works with both Android and iPhone. Data is organised into services and characteristics. A bit more code to set up.

Classic Bluetooth serial

#include "BluetoothSerial.h"

BluetoothSerial SerialBT;

void setup() {
  Serial.begin(115200);
  SerialBT.begin("Robodarshan-Bot");     // the name your phone will see
}

void loop() {
  if (SerialBT.available()) Serial.write(SerialBT.read());   // phone to computer
  if (Serial.available())   SerialBT.write(Serial.read());   // computer to phone
  delay(5);
}

Pair your phone with “Robodarshan-Bot”, open a Bluetooth serial terminal app and send characters like F or S. It is the same idea as the HC-05 module in your Stage 1 project, but built into the ESP32.

BLE in a nutshell

A BLE device is a server that offers services. A service contains characteristics, which are like named mailboxes holding a value. A phone app (the client) can write a value, read it, or ask to be notified when it changes. Every service and characteristic has a UUID, a long unique ID.

#include <BLEDevice.h>
#include <BLEServer.h>
#include <BLEUtils.h>

// Example UUIDs. For your own robot generate new ones (uuidgenerator.net).
#define SERVICE_UUID        "4fafc201-1fb5-459e-8fcc-c5c9c331914b"
#define CHARACTERISTIC_UUID "beb5483e-36e1-4688-b7f5-ea07361b26a8"

class CommandCallbacks : public BLECharacteristicCallbacks {
  void onWrite(BLECharacteristic* characteristic) {
    auto value = characteristic->getValue();     // what the phone wrote
    if (value.length() > 0) {
      Serial.print("Command: ");
      Serial.println(value[0]);                  // for example 'F', 'B', 'L', 'R', 'S'
    }
  }
};

void setup() {
  Serial.begin(115200);
  BLEDevice::init("Robodarshan-Bot");
  BLEServer* server = BLEDevice::createServer();
  BLEService* service = server->createService(SERVICE_UUID);
  BLECharacteristic* command = service->createCharacteristic(
      CHARACTERISTIC_UUID, BLECharacteristic::PROPERTY_WRITE);
  command->setCallbacks(new CommandCallbacks());
  service->start();
  BLEDevice::getAdvertising()->addServiceUUID(SERVICE_UUID);
  BLEDevice::getAdvertising()->start();
}

void loop() {}

To test, install a free BLE app such as nRF Connect on your phone, connect to “Robodarshan-Bot”, open the service and write a value to the characteristic. The character you send appears in the Serial Monitor.

“Sketch too big” error?

BLE and Wi-Fi libraries are large. In Tools → Partition Scheme choose Huge APP to leave more room for your program.

ESP32 robot control

Now combine everything: an ESP32 that creates its own Wi-Fi network, serves a control page, and drives two motors through a TB6612FNG motor driver. This is the starting point for your Stage 2 robots.

The TB6612FNG in brief

  • VM: motor supply from the battery (about 4.5 V to 13.5 V). VCC: the logic supply; connect it to the ESP32's 3.3 V.
  • It drives two motors (channels A and B). Each channel has two direction pins (AIN1, AIN2 / BIN1, BIN2) and one speed pin (PWMA / PWMB).
  • STBY must be HIGH or the driver stays switched off.
  • It handles about 1.2 A continuously per channel, which is enough for small gear motors.
IN1IN2Motor does
HIGHLOWSpins one way (speed set by PWM)
LOWHIGHSpins the other way
LOWLOWStops (motor freewheels)
HIGHHIGHBrakes

Which direction counts as “forward” depends on how you wired the motor. If a wheel spins backwards, swap its two motor wires or swap the signs in your code.

Before you power it
  • Power the motors from the battery through VM, never from the ESP32's 3V3 pin or USB.
  • Join the battery ground, driver ground and ESP32 ground. Without a common ground nothing works properly.
  • Lift the wheels off the table for the first test.

The code

Motor speed is set with PWM: the ESP32 switches the pin on and off very fast, and the share of time it is on decides how fast the motor turns. The ESP32 generates PWM with its ledc peripheral. The commands changed between version 2 and version 3 of the ESP32 Arduino core, so the code below works with both.

#include <WiFi.h>
#include <WebServer.h>

// TB6612FNG pins (change them to match your wiring)
const int PWMA = 25, AIN1 = 26, AIN2 = 27;
const int PWMB = 13, BIN1 = 32, BIN2 = 33;
const int STBY = 4;

const int PWM_FREQ = 20000;              // 20 kHz is above what we can hear
const int PWM_BITS = 8;                  // duty cycle from 0 to 255
const int SPEED = 150;                   // start slow

WebServer server(80);
unsigned long lastCommandMs = 0;

// ---- PWM helpers (work on ESP32 core 2.x and 3.x) ----
void pwmBegin(int pin, int channel) {
#if defined(ESP_ARDUINO_VERSION_MAJOR) && ESP_ARDUINO_VERSION_MAJOR >= 3
  ledcAttach(pin, PWM_FREQ, PWM_BITS);
#else
  ledcSetup(channel, PWM_FREQ, PWM_BITS);
  ledcAttachPin(pin, channel);
#endif
}

void pwmWrite(int pin, int channel, int duty) {
#if defined(ESP_ARDUINO_VERSION_MAJOR) && ESP_ARDUINO_VERSION_MAJOR >= 3
  ledcWrite(pin, duty);
#else
  ledcWrite(channel, duty);
#endif
}

// ---- motor control ----
// speed: -255 (full reverse) to +255 (full forward)
void setMotor(int in1, int in2, int pwmPin, int channel, int speed) {
  speed = constrain(speed, -255, 255);
  digitalWrite(in1, speed > 0);
  digitalWrite(in2, speed < 0);
  pwmWrite(pwmPin, channel, abs(speed));
}

void drive(int left, int right) {
  setMotor(AIN1, AIN2, PWMA, 0, left);
  setMotor(BIN1, BIN2, PWMB, 1, right);
}

// ---- web page ----
const char PAGE[] PROGMEM = R"rawliteral(
<!DOCTYPE html><html><head>
<meta name="viewport" content="width=device-width, initial-scale=1">
<style>
  body { font-family: sans-serif; text-align: center; user-select: none; }
  button { width: 28vw; height: 22vw; margin: 4px; font-size: 8vw; touch-action: manipulation; }
</style></head><body>
<h2>Robodarshan Bot</h2>
<div><button onpointerdown="press('forward')" onpointerup="release()" onpointerleave="release()">&#9650;</button></div>
<div>
  <button onpointerdown="press('left')"  onpointerup="release()" onpointerleave="release()">&#9664;</button>
  <button onpointerdown="press('back')"  onpointerup="release()" onpointerleave="release()">&#9660;</button>
  <button onpointerdown="press('right')" onpointerup="release()" onpointerleave="release()">&#9654;</button>
</div>
<script>
  let timer = null;
  function send(cmd) { fetch('/' + cmd); }
  function press(cmd) { release(); send(cmd); timer = setInterval(() => send(cmd), 200); }
  function release() { if (timer) { clearInterval(timer); timer = null; send('stop'); } }
</script></body></html>
)rawliteral";

void command(int left, int right) {
  drive(left, right);
  lastCommandMs = millis();
  server.send(200, "text/plain", "OK");
}

void setup() {
  Serial.begin(115200);

  pinMode(AIN1, OUTPUT); pinMode(AIN2, OUTPUT);
  pinMode(BIN1, OUTPUT); pinMode(BIN2, OUTPUT);
  pinMode(STBY, OUTPUT);
  digitalWrite(STBY, HIGH);              // enable the driver
  pwmBegin(PWMA, 0);
  pwmBegin(PWMB, 1);
  drive(0, 0);

  WiFi.mode(WIFI_AP);
  WiFi.softAP("Robodarshan-Bot", "robot1234");
  Serial.print("Open http://");
  Serial.println(WiFi.softAPIP());       // 192.168.4.1

  server.on("/", []() { server.send_P(200, "text/html", PAGE); });
  server.on("/forward", []() { command( SPEED,  SPEED); });
  server.on("/back",    []() { command(-SPEED, -SPEED); });
  server.on("/left",    []() { command(-SPEED,  SPEED); });
  server.on("/right",   []() { command( SPEED, -SPEED); });
  server.on("/stop",    []() { command(0, 0); });
  server.begin();
}

void loop() {
  server.handleClient();

  // Safety: stop if the phone has gone quiet (out of range, page closed)
  if (millis() - lastCommandMs > 600) drive(0, 0);
}

Join the “Robodarshan-Bot” network from your phone, open 192.168.4.1 in the browser and hold the arrow buttons. While you hold a button the page keeps sending the command every 200 ms; when you let go, or the signal is lost, the robot stops by itself. That fail-safe is a good habit for every robot you build.

This is starter code

It is written to be a clear starting point, but pin numbers, motor directions and a good SPEED depend on your own robot. Test with the wheels lifted and adjust. Left and right turns here spin the robot on the spot (one wheel each way).

Key takeaways

  • Serial is your debugging tool. Match the baud rate and print sparingly.
  • UART is two wires, crossed TX to RX, with a shared ground and the same baud rate on both sides.
  • I²C shares two wires between many devices by address; scan the bus first when a device is silent.
  • SPI is fast, using three shared wires plus one chip-select wire per device.
  • The ESP32 has Wi-Fi (station or access point), a web server, and both Bluetooth types: classic serial and BLE.
  • Drive motors from a battery through a driver such as the TB6612FNG, keep a common ground, and always add a fail-safe stop.
