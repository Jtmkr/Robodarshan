A method for debugging, and the tools

Every robot misbehaves. The difference between a team that fixes it in ten minutes and a team that fights for a week is not talent, it is method. Debugging is the search for the cause of a symptom, and a random search is slow. A systematic one is fast.

The five rules

  1. Reproduce it. Make the fault happen on purpose. If you cannot make it happen, you cannot know whether you fixed it. Note the conditions: battery level, floor, speed, which button.
  2. Isolate it. Find which subsystem is guilty: power, sensors, motors, encoders or communication. Lift the wheels, unplug things, run one part alone.
  3. Test each subsystem alone with a small test sketch, not with your full robot program. A bug in your PID cannot hide a bad sensor if the sketch only prints the sensor.
  4. Change one thing at a time. If you change the code, the wire and the battery together and it works, you have learned nothing.
  5. Write it down. Keep a notebook or a text file: what you changed, what you measured, what happened. Numbers you wrote down tomorrow are worth more than a memory of “it seemed better”.

Your tools

Multimeter

Measures voltage, continuity (beeps for a connected wire) and resistance. It finds loose wires, shorts and sagging supplies. Learn it first.

Serial Monitor and Plotter

Print values at 115200 baud. The Serial Plotter (Tools menu in the Arduino IDE) draws printed numbers as lines, which shows noise and drift instantly.

Logic analyzer

A cheap USB one with 8 channels records digital signals (encoder A and B, I²C, UART) and shows them as waveforms in free software. It shows what really happened on the wire.

Oscilloscope (optional)

Shows analog shapes: a sagging 5 V rail, noise spikes, ringing. Very useful, but not required to start.

LED or buzzer

A way to tell what the robot is doing when the cable is unplugged and the robot is running on the floor.

Test sketches

Tiny programs that exercise one part. You will write several below, and keep them in a folder named tests.

Here is a small helper you will reuse to signal events when no computer is attached. The on-board LED of most DevKits is on GPIO2.

const int LED_PIN = 2;               // on-board LED on most DevKits

// Blink n times: a cheap way to show "I reached this point" without Serial
void blink(int n) {
  pinMode(LED_PIN, OUTPUT);
  for (int i = 0; i < n; i++) {
    digitalWrite(LED_PIN, HIGH); delay(120);
    digitalWrite(LED_PIN, LOW);  delay(120);
  }
}

Sensor calibration

The QTR-8A gives 8 analog values. On this build they are read through two ADS1115 chips (the sensors lesson explains how). The sensor shines infrared light down and measures how much comes back. A dark line reflects little light and gives a higher output voltage; a white floor reflects a lot and gives a lower one. Calibration records the lowest and highest value each sensor sees on your floor and line, then scales every reading to 0 to 1000 (1000 = darkest). Without it, every channel has a different “white” and “black”, and the line position comes out wrong.

A diagnostic sketch: raw values, min, max and bars

This sketch does not depend on your calibration routine. It tracks the min and max of every channel while you slide the robot over the line, and prints a bar for each channel so you can see what the sensor sees. It uses sensorsBegin() and readRaw() from the sensors lesson.

// Sensor diagnostic: raw value, min/max seen, calibrated 0..1000 and a bar.
const int NUM_SENSORS = 8;
const uint16_t MIN_SPAN = 2000;      // ASSUMPTION: a healthy channel spans more than this.
                                     // Depends on your ADS1115 gain: tune it.
uint16_t rawMin[NUM_SENSORS], rawMax[NUM_SENSORS];

void setup() {
  Serial.begin(115200);
  sensorsBegin();
  for (int i = 0; i < NUM_SENSORS; i++) { rawMin[i] = 65535; rawMax[i] = 0; }
  Serial.println("Slide the sensor slowly across the line and the floor...");
}

void loop() {
  uint16_t raw[NUM_SENSORS];
  readRaw(raw);

  for (int i = 0; i < NUM_SENSORS; i++) {
    if (raw[i] < rawMin[i]) rawMin[i] = raw[i];
    if (raw[i] > rawMax[i]) rawMax[i] = raw[i];

    uint16_t span = rawMax[i] - rawMin[i];
    long cal = 0;
    if (span > 0) cal = (long)(raw[i] - rawMin[i]) * 1000L / span;   // 0..1000
    cal = constrain(cal, 0, 1000);

    Serial.print(i);
    Serial.print(": raw=");  Serial.print(raw[i]);
    Serial.print(" span=");  Serial.print(span);
    Serial.print(" cal=");   Serial.print(cal);
    Serial.print(" ");
    for (int b = 0; b < cal / 100; b++) Serial.print('#');      // bar, one # per 100
    if (span < MIN_SPAN) Serial.print("   <-- LOW SPAN: dead, saturated or not swept");
    Serial.println();
  }
  Serial.println("----");
  delay(250);
}

Reading the output: over the white floor every bar should be short, and over the line the sensors that are on the line should show long bars. A channel with a tiny span is suspicious. A channel whose raw value never changes is dead or saturated.

Calibrate on the real surface, then check the result

Calibrate at the competition track, in the light of the competition hall, with the real battery. After calibration, put the robot with the line centred and check that the two centre sensors read high and the outer ones read low. Then move it left and right by a few millimetres and watch the position change smoothly.

Motor matching

Two motors with the same part number are never identical. One has more friction, one a slightly tighter gearbox, one a weaker magnet, one a worse connection. Give both the same PWM and the robot slowly curves. That is not a bug in your code, it is physics, and you fix it by measuring.

Finding the trim factor

The idea: drive both wheels with the same PWM for a fixed time, then compare encoder counts. The wheel that moved fewer counts is the slower one. Suppose we command PWM 120 on both sides for 2 seconds and read:

  • left = 6400 counts, right = 5900 counts.

The left motor is faster. Its trim factor is trimL = right / left = 5900 / 6400 = 0.92. Multiply every left command by 0.92 and the two sides should now match at this speed. If the right were faster you would use trimR = left / right.

(These numbers are an example, not a measurement. For reference, a 300 RPM wheel with 1400 counts per revolution makes at most about 7000 counts per second with no load; the encoder constants are the assumptions from the other lessons.)

// Motor matching test. LIFT THE WHEELS. Uses drive(), leftTicks(), rightTicks()
// and resetEncoders() from the earlier lessons.
const int  TEST_PWM = 120;           // try a speed you actually use in a run
const unsigned long RUN_MS = 2000;

// Which PWM makes a wheel start to turn? (dead zone)
int findDeadZone(bool leftSide) {
  for (int pwm = 0; pwm <= 150; pwm += 5) {
    resetEncoders();
    if (leftSide) drive(pwm, 0); else drive(0, pwm);
    delay(300);
    drive(0, 0);
    delay(200);
    long t = leftSide ? leftTicks() : rightTicks();
    if (abs(t) >= 10) return pwm;      // it moved: this is the dead-zone edge
  }
  return -1;                           // never moved: check wiring
}

void setup() {
  Serial.begin(115200);
  motorsBegin();
  encodersBegin();
  delay(2000);                         // time to put the robot down safely

  Serial.print("Dead zone left  = "); Serial.println(findDeadZone(true));
  Serial.print("Dead zone right = "); Serial.println(findDeadZone(false));

  // Equal PWM on both sides, compare counts
  resetEncoders();
  drive(TEST_PWM, TEST_PWM);
  delay(RUN_MS);
  drive(0, 0);
  delay(300);
  long l = abs(leftTicks());
  long r = abs(rightTicks());
  Serial.print("left = ");  Serial.print(l);
  Serial.print("  right = "); Serial.println(r);

  if (l == 0 || r == 0) {
    Serial.println("A wheel did not count. Check motor or encoder wiring first.");
    return;
  }
  float trimL = 1.0, trimR = 1.0;
  if (l > r) trimL = (float)r / l;     // left is faster: slow it down
  else        trimR = (float)l / r;    // right is faster: slow it down
  Serial.print("trimL = "); Serial.println(trimL, 3);
  Serial.print("trimR = "); Serial.println(trimR, 3);
}

void loop() {}

Then use the numbers in one place so they are easy to change:

float TRIM_L = 0.92;                 // from the test above (example value)
float TRIM_R = 1.00;

void driveTrimmed(int left, int right) {
  drive((int)(left * TRIM_L), (int)(right * TRIM_R));
}
A trim is not a cure for everything

Repeat the test at two or three speeds, with the same battery charge. If the trim changes a lot with speed, you are seeing a dead zone as well, and a closed-loop controller that uses the encoders (the PID lessons) will do far better than a single number. Also check for mechanical causes first: a wheel rubbing the chassis, a loose wheel, or a bent axle.

Encoder errors

With the assumptions of this course (7 pulses per revolution per channel on the motor shaft, 50:1 gearbox, x4 decoding) one wheel revolution should give 1400 counts. If your motor is different, replace these with your datasheet values. Encoder errors usually look like a robot that drives the wrong distance or turns the wrong angle.

3.3 V only

The ESP32 inputs are 3.3 V devices. Many encoder boards can be powered from 3.3 V to 5 V and then give outputs at the same level. If you power an encoder from 5 V, its outputs can exceed 3.3 V and harm the ESP32. Check your motor's datasheet and use 3.3 V.

The one-revolution test

This is the best single test of an encoder. Lift the robot, press the button, turn one wheel forward by hand through exactly one revolution (use a mark on the tyre), and press the button again to see the count. It uses encodersBegin(), leftTicks(), rightTicks() and resetEncoders() from the earlier lessons and the button on GPIO14.

// Encoder one-revolution test. Turn ONE wheel by hand through one revolution.
const int BTN = 14;                  // button to GND, INPUT_PULLUP
const int EXPECTED = 1400;           // ASSUMPTION: 7 x 50 x 4. Use your own motor's number.

void setup() {
  Serial.begin(115200);
  pinMode(BTN, INPUT_PULLUP);
  pinMode(34, INPUT);  pinMode(35, INPUT);   // for the raw pin monitor below
  encodersBegin();
  resetEncoders();
  Serial.println("Turn a wheel once, then press the button.");
}

void loop() {
  static unsigned long lastPrint = 0;
  if (millis() - lastPrint > 200) {          // live view of both counters
    lastPrint = millis();
    Serial.print("L = "); Serial.print(leftTicks());
    Serial.print("   R = "); Serial.print(rightTicks());
    Serial.print("   A/B(left) = "); Serial.print(digitalRead(34));
    Serial.println(digitalRead(35));
  }

  if (digitalRead(BTN) == LOW) {
    delay(30);                                 // simple debounce
    long l = leftTicks(), r = rightTicks();
    Serial.println("=== result ===");
    Serial.print("left = ");  Serial.print(l);
    Serial.print("  error = "); Serial.print((abs(l) - EXPECTED) * 100.0 / EXPECTED, 1); Serial.println(" %");
    Serial.print("right = "); Serial.print(r);
    Serial.print("  error = "); Serial.print((abs(r) - EXPECTED) * 100.0 / EXPECTED, 1); Serial.println(" %");
    resetEncoders();
    while (digitalRead(BTN) == LOW) delay(10); // wait for release
  }
}

Reading the result: when you turn a wheel by hand, expect the count to be close to 1400, with a small error from where you started and stopped (a few counts, or a percent or so). The sign tells you the direction: forward should count up in both wheels. A result near 700 or 350 points to the decoding, not the wiring. If the counter does not change at all, watch the raw A/B pin states: they should change as the wheel turns. If they do not, the wiring is the problem.

The interrupt handler rules
  • Mark handlers IRAM_ATTR on the ESP32 and keep them to a few lines: read the pins, update one counter.
  • Variables shared with the main program must be volatile; read a multi-byte counter with interrupts briefly disabled if you need a perfectly consistent value.
  • No Serial, delay(), I²C or Wi-Fi calls inside an ISR.
  • Roughly, one wheel at full speed makes thousands of edges per second, so two wheels give several thousand interrupts per second. That is fine for the ESP32 if each handler is short. Measure it, do not trust this estimate blindly.

Communication issues

Your robot talks to its chips on shared wires. When a chip goes silent, the symptoms are things like an OLED that stays blank, an MPU6050 that returns zeros, or sensors that suddenly freeze. A good rule: always scan first.

I²C

Run the scanner from Lesson 01. On this robot you expect four things: 0x3C (OLED), 0x48 and 0x49 (the two ADS1115 chips) and 0x68 (MPU6050). This variation checks the list and prints the error code for anything missing:

#include <Wire.h>

const uint8_t EXPECTED[] = { 0x3C, 0x48, 0x49, 0x68 };
const char*   NAMES[]    = { "OLED", "ADS1115 #0", "ADS1115 #1", "MPU6050" };

void setup() {
  Serial.begin(115200);
  Wire.begin(21, 22);                // SDA, SCL
  Wire.setClock(400000);
}

void loop() {
  for (int i = 0; i < 4; i++) {
    Wire.beginTransmission(EXPECTED[i]);
    byte err = Wire.endTransmission();     // 0 = answered
    Serial.print(NAMES[i]);
    Serial.print(" (0x"); Serial.print(EXPECTED[i], HEX); Serial.print("): ");
    if (err == 0) Serial.println("OK");
    else { Serial.print("MISSING, error "); Serial.println(err); }
  }
  Serial.println("----");
  delay(2000);
}

The error code gives a clue: 2 means no device answered at that address (wiring or address), 3 means the device did not accept data, and 4 is an unknown error (the ESP32 core can also report a timeout code, often a stuck bus).

Recovering a stuck bus: a device that thinks it is in the middle of a byte keeps SDA low until it sees enough clock pulses. You can supply them by hand and then send a STOP:

const int SDA_PIN = 21, SCL_PIN = 22;

void i2cRecover() {
  Wire.end();                        // release the I2C peripheral
  pinMode(SDA_PIN, INPUT_PULLUP);
  pinMode(SCL_PIN, OUTPUT);
  for (int i = 0; i < 9 && digitalRead(SDA_PIN) == LOW; i++) {   // up to 9 clock pulses
    digitalWrite(SCL_PIN, LOW);  delayMicroseconds(5);
    digitalWrite(SCL_PIN, HIGH); delayMicroseconds(5);
  }
  // Send a STOP: SDA goes low to high while SCL is high
  pinMode(SDA_PIN, OUTPUT);
  digitalWrite(SDA_PIN, LOW);  delayMicroseconds(5);
  digitalWrite(SCL_PIN, HIGH); delayMicroseconds(5);
  digitalWrite(SDA_PIN, HIGH); delayMicroseconds(5);
  Wire.begin(SDA_PIN, SCL_PIN);      // start the bus again
  Wire.setClock(400000);
}

If the bus is stuck again and again, the recovery is only a band-aid. Look for a power dip, a loose wire or noise.

UART and SPI basics

  • UART: both sides must use the same baud rate and format. Garbage characters usually mean a baud mismatch. Remember to cross TX and RX, and join the grounds. Keep to 3.3 V levels with the ESP32.
  • SPI: the mode (0 to 3), bit order and clock speed must match the device's datasheet. Check that the chip-select pin goes low for each transfer and that MISO, MOSI and SCK are not swapped. Slow the clock to test.

Wi-Fi issues

  • While Wi-Fi is on, ADC2 pins cannot be read with analogRead(). Put analog inputs on ADC1 (GPIO32 to 39).
  • The classic ESP32 supports 2.4 GHz only; it cannot see a 5 GHz-only network.
  • Wi-Fi uses short bursts of high current, which can cause brownouts on a weak supply (see the next section).

Power issues

A huge share of “mystery” robot bugs are power problems. A DC motor that starts draws a big burst of current (a start-up or stall current much higher than its running current). That burst pulls the battery voltage down. If the supply feeding the ESP32 dips too low even for a moment, the ESP32 resets and prints Brownout detector was triggered. Then the program restarts, the motors start again, and the cycle repeats.

Do not just turn the detector off

It is possible to disable the ESP32 brownout detector in software. That hides the symptom, but the chip then runs below its voltage limits and can behave in random and dangerous ways. Fix the supply instead.

Measure it under load

A multimeter reading with the motors idle tells you almost nothing, because the fault only exists when the current flows. Measure the battery pins, the VM pin of the motor driver and the 5 V rail while the motors run, and watch the lowest value. A meter's display is slow and can miss a very short dip; a logger or a scope shows it properly. A simple logger is the sketch below.

It reads the battery through a resistor divider. A 3S pack reaches 12.6 V, far above the ESP32's 3.3 V limit. With 47 kΩ from battery positive to the pin and 12 kΩ from the pin to ground (the same divider as in Lesson 11), the pin sees 12.6 V × 12 / 59, which is about 2.56 V. Use 1% resistors, and always check the resistor values before you connect the battery.

Assumptions in this sketch
  • Divider: 47 kΩ (top) and 10 kΩ (bottom). Change the constants if you use other values.
  • The battery divider goes on GPIO39, an ADC1 input-only pin that works even when Wi-Fi is on. That is why the right encoder's B channel is on GPIO18 in this course's pin map. If you wire your robot differently, use any other ADC1 pin (GPIO32 to 39) that is free.
  • The low-battery limit of 9.9 V is about 3.3 V per cell under load. It is only an example: follow the advice on your own pack.
// Battery logger: prints the battery voltage and the lowest value seen each second.
const int   BATT_PIN  = 39;          // ADC1, input-only pin (kept free for this in the pin map)
const float R_TOP     = 47000.0;
const float R_BOTTOM  = 12000.0;
const float DIVIDER   = (R_TOP + R_BOTTOM) / R_BOTTOM;   // 4.92
const float CAL       = 1.00;        // adjust until the reading matches a multimeter
const float LOW_BATT_V = 9.9;        // example limit under load, 3S pack

float readBatteryVolts() {
  long sum = 0;
  for (int i = 0; i < 16; i++) sum += analogReadMilliVolts(BATT_PIN);  // average noise away
  float pinVolts = sum / 16.0 / 1000.0;
  return pinVolts * DIVIDER * CAL;
}

float minV = 99.0;
unsigned long lastPrint = 0;

void setup() {
  Serial.begin(115200);
  analogSetPinAttenuation(BATT_PIN, ADC_11db);   // allow up to about 3.1 V at the pin
  // motorsBegin(); drive(150, 150);   // enable to see the sag when the motors run
}

void loop() {
  float v = readBatteryVolts();
  if (v < minV) minV = v;

  if (millis() - lastPrint >= 1000) {
    lastPrint = millis();
    Serial.print("battery = "); Serial.print(v, 2);
    Serial.print(" V   lowest this second = "); Serial.println(minV, 2);
    if (minV < LOW_BATT_V) Serial.println("LOW BATTERY: stop and recharge");
    minV = 99.0;
  }
}

Compare the reading with your multimeter and adjust CAL. Run the motors and watch the lowest value. If it falls a lot when the motors start, the supply is the problem. If you start to see the lowest value near your cut-off, the battery is nearly empty.

Low-battery behaviour and good habits

  • A LiPo should not be run flat. Many packs state a minimum per-cell voltage on the label; stay above it. A common general advice is not to go below about 3.0 V per cell (9.0 V for 3S) at rest, and many people stop earlier. Follow your pack's label.
  • As the battery empties, motors slow down and match worse, and the 5 V buck may start to drop out. Always compare tests at a similar charge.
  • Use a LiPo alarm or a monitor, and never leave a charging LiPo unattended.
  • Use locking connectors (XT60, JST-XH) for power, and check them for heat after a run.

The master debugging checklist

When something is wrong and you do not know where to start, go through this list in order. Tick each item, and write down what you found.

  1. Safety: wheels lifted, battery connected correctly, nothing hot or smelling of burning?
  2. Battery: fully charged? Measure it at rest and under load.
  3. Power rails: VM, 5 V and 3.3 V correct with the motors running?
  4. Connections: wiggle test; continuity on every power and ground wire; all grounds common?
  5. Serial: boot message present, no “Brownout” or “Guru Meditation” messages?
  6. I²C scan: are 0x3C, 0x48, 0x49 and 0x68 all there?
  7. Sensors: run the sensor diagnostic. Good span on all 8 channels? Calibrated on this surface and light?
  8. Encoders: one-revolution test about 1400, forward counts positive, both wheels consistent?
  9. Motors: both turn the right way; dead zones known; trim measured at the speed you use?
  10. Code: a recent change? Undo it and test again. Are your constants (pins, wheel size, speeds) right?
  11. Environment: same floor, light and battery level as the last good run?
  12. Notes: write down the fix and the date.

Three case studies

Case 1: the robot veers left

Symptom: with the same command on both wheels, the robot slowly curves left on the floor.

  1. Reproduce: drive straight at one speed on the same floor three times. It always curves left, so the cause is consistent, not random.
  2. Isolate: lift the wheels and look. Both wheels turn forward, so the wiring is fine. Run the motor matching sketch.
  3. Measure: equal PWM 120 for 2 s gives left = 5900 and right = 6400. The left wheel is slower, which is why the robot veers to the left.
  4. Change one thing: set TRIM_R = 5900.0 / 6400.0 = 0.92 and use driveTrimmed().
  5. Retest: it now goes straight at 120. At a slower speed it still veers a little. That means a dead-zone effect on the left motor, so measure the dead zones, add a minimum PWM, and later use a speed controller with encoders.

Case 2: the robot resets when it starts

Symptom: the robot starts, the motors jerk, the ESP32 restarts, and the Serial Monitor shows Brownout detector was triggered.

  1. Isolate: a reset exactly when the motors start points to power, not code.
  2. Measure: run the battery logger. With the motors on, the lowest voltage in one second drops far below the resting voltage. The pack was also only half charged.
  3. Change one thing: first charge the battery. The reset happens less often but still happens.
  4. Next: inspect the wiring. A thin wire and a worn connector are between the battery and the driver and the buck module. Replace them with thicker wire and a proper XT60.
  5. Next: add a bulk capacitor near the driver VM pin, and ramp the PWM up over a short time instead of jumping to a high value.
  6. Verify: the lowest voltage no longer falls near the limit, and the resets are gone. Write down which change helped.

Case 3: the junction is never detected

Symptom: on a track with a crossing, the robot follows the line but never realises there is a junction.

  1. Reproduce: place the robot on the crossing, and print the 8 calibrated values.
  2. Look: the junction logic needs the outer sensors (0 and 7) to read dark together with the centre ones. Channels 1 to 6 are high, channel 0 is low, and channel 7 stays at a fixed value.
  3. Isolate: channel 7 never changes in the sensor diagnostic. Its span is tiny. A wire or solder joint is at fault, or that ADS1115 input is not read.
  4. Test: multimeter on the channel 7 wire: it has no continuity to the connector. Re-solder the connector pin.
  5. Retest: channel 7 now moves. Channel 0 still reads low over the line. The sensor is higher at the edge because the array is tilted, so measure the height at both ends and straighten it. Calibrate again.
  6. Verify: both outer channels go high on the crossing. The junction detection works. Adjust the threshold only after the hardware is right.
The pattern in all three cases

Measure first, change one thing, and check the result. In every case the fix came from a number, not from a guess.

Key takeaways

  • Debug with a method: reproduce, isolate, test each subsystem alone, change one thing at a time, and write down results.
  • Use a multimeter, the Serial Monitor and Plotter, and a cheap logic analyzer. A scope is a bonus.
  • Sensor calibration: calibrate on the real floor and light, at the right height; check the span of every channel and watch for dead or saturated ones.
  • Motor matching: no two motors are equal. Compare encoder counts at equal PWM to find a trim factor, and measure the dead zones.
  • Encoder errors: do the one-revolution test (about 1400 counts with our assumptions). Check direction, decoding, noise, wiring, pull-ups, and keep the ISR short.
  • Communication: scan the I²C bus first. Different ADDR levels for the two ADS1115 chips, working pull-ups, short wires and a recovery routine for a stuck bus.
  • Power: measure VM and 5 V under load. Most brownouts come from battery sag, thin wires, loose connectors or weak converters. Fix the supply and never just disable the detector.
  • Work through the master checklist in order, and keep a written log of your findings.
