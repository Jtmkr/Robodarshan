Error and setpoint: the feedback loop

So far your robot has mostly been giving orders: “motors at 150”. But 150 does not mean the same thing on a full battery and on a tired one, on a smooth floor and on a carpet, or for the left motor and the right motor. A controller fixes this by looking at what actually happened and correcting the next command. That is called feedback (or closed-loop control), and PID is the most popular way to do it.

Three words matter before anything else:

Setpoint (r)

What you want: a wheel speed of 3000 counts per second, or “line exactly under the middle of the array”.

Measurement (y)

What a sensor says you have: speed from the encoder, or line position from the QTR-8A.

Error (e)

The gap: e = r − y. Zero means perfect. The sign tells you which way to push.

Every pass of the loop does the same four things: measure, compute the error, compute the command, apply it. The only thing PID decides is how to turn the error into a command.

Starter code and assumptions

The code in this lesson is starter code written without access to your hardware. Pins, directions and every gain value are examples: test and tune them on your real robot. It uses the helpers from earlier lessons (drive(), leftTicks(), readLinePosition()) and the millis() / micros() timing from Lesson 02. Motor numbers (1400 encoder counts per wheel turn, 34 mm wheel) are the assumed N20 values from Lesson 03 and 05: use your own.

P, I and D: three ways to look at the error

PID adds together three simple ideas. Each looks at the same error, but from a different angle in time.

P: proportional, the present

“The further I am from the goal, the harder I push.” The P term is Kp × e. Think of steering a bicycle toward a gap between two cones: if you are far to the left you turn the handlebar a lot, if you are slightly left you turn a little. P alone is simple and fast, but it has two weaknesses. With a small gain it never quite reaches the setpoint (to keep pushing it needs some leftover error), and with a large gain it overshoots and wobbles.

I: integral, the past

“I have been a little short for a while, so push a little more.” The I term adds up the error over time: Ki × (sum of e × dt). Imagine a robot that drives slightly uphill. P alone settles a bit under the target speed. The integral keeps growing as long as any error remains, so it slowly adds just enough extra push to remove it. The price is that it reacts slowly and, because it remembers, it can overshoot.

D: derivative, the trend

“I am approaching the goal quickly, so ease off before I arrive.” The D term is Kd × (change of e per second). It is like a driver who brakes early because the stop line is coming up fast. D acts against fast changes, so it damps overshoot and wobble. It also amplifies noise, because noise is a lot of tiny fast changes.

What each term does to a step response

Test a controller by suddenly changing the setpoint (a step) and watching the response. Four numbers describe it: rise time (how fast it first gets there), overshoot (how far it goes past), settling time (how long until it stays near the target) and steady-state error (what is left at the end).

The PID equation

Put the three terms together and you get the command u that goes to the motors:

u(t) = Kp · e(t)  +  Ki · ∫ e(t) dt  +  Kd · de(t)/dt

The ∫ sign means “the running total of the error over time” and de/dt means “how fast the error is changing”. That is the continuous version. Your microcontroller works in steps, one every dt seconds, so the version you actually code is:

integral   = integral + e · dt
derivative = (e − lastError) / dt
u = Kp · e + Ki · integral + Kd · derivative
lastError = e

An integral becomes a running sum and a derivative becomes “this error minus last error, divided by the time between them”. Here is the whole thing in C++, using the names that the rest of the course uses:

struct PidGains { float kp, ki, kd; };
struct PidState { float integral = 0; float lastError = 0; };

// One PID step. Call it at a steady rate.
// integralLimit: the integral is clamped to +/- this value (use a value > 0).
float pidCompute(const PidGains& g, PidState& s, float error,
                 float dtSeconds, float integralLimit) {
  if (dtSeconds <= 0) return g.kp * error;            // guard against dt = 0

  // I: accumulate, then clamp (anti-windup)
  s.integral += error * dtSeconds;
  s.integral = constrain(s.integral, -integralLimit, integralLimit);

  // D: slope of the error since the last call
  float derivative = (error - s.lastError) / dtSeconds;
  s.lastError = error;

  return g.kp * error + g.ki * s.integral + g.kd * derivative;
}

// Forget the past: call when the controller starts, stops or restarts.
void pidReset(PidState& s) {
  s.integral = 0;
  s.lastError = 0;
}

Notes on this function:

  • It does not clamp the final output, because only you know the limits (for example ±255 for PWM). The caller does that.
  • integralLimit limits the stored integral (units: error × seconds). The most the I term can ever contribute is Ki × integralLimit, so choose it from the output range you are willing to give the I term.
  • pidReset() is a small extra helper. Without it, the first call after a pause computes a huge derivative from a stale lastError.
  • Gains depend on the units of error and output. A Kp that works when the error is in encoder counts per second will be wrong when the error is in line-position units. Gains are never universal.
Printing the three terms

When something misbehaves, print the P, I and D parts separately instead of only the total. You can then see which term is doing the damage. A quick way is to compute them with the same formulas in a temporary copy of the function.

Overshoot, oscillation and stability

Real robots do not respond instantly: a motor needs time to speed up, wheels slip, sensors are read a few milliseconds late. Because of this lag, the controller keeps pushing for a moment after the goal has been reached, and the robot goes past it. That is overshoot. The error now has the opposite sign, so the controller pushes back, overshoots again, and you get oscillation: a repeating wobble around the target.

  • Under-damped: fast, but overshoots and rings. A line follower in this state snakes across the line.
  • Critically damped: the fastest response that does not overshoot. A good target for a controlled speed.
  • Over-damped: no overshoot, but sluggish. A robot like this reacts too slowly in a sharp turn.

For robots a little overshoot is often acceptable if the response is much faster. Aiming for slightly under-damped is common for line followers; zero overshoot matters more for something like stopping at a wall.

Stability

A system is stable if the wobble dies away (or never starts) and the output stays bounded. It is unstable if the wobble grows until something saturates: the motors hit full power in both directions, and the robot shakes itself off the line. In between there is a boundary where the wobble neither grows nor shrinks: a steady oscillation. You will use exactly that boundary in the tuning method below.

Why too-high gains cause trouble

Because of delay and lag, a correction arrives late. A mild correction arriving late is harmless. A strong correction arriving late pushes the robot past the target by more than the original error, so each swing is bigger than the last. High Kp and high Ki make strong, late corrections. Slow loop rates and sensor delay make the corrections later. That is why a loop that is stable at 100 Hz can become unstable at 20 Hz with the same gains.

Tuning: finding Kp, Ki and Kd

Tuning means finding gains that give a response you like. There is no formula that knows your robot's weight, motors and floor, so you tune by experiment. Change one gain at a time, and write down what you tried.

Manual tuning, step by step

  1. Set Ki = 0 and Kd = 0. Start with a small Kp. Keep the robot lifted or the wheels off the ground for the first tests if you are tuning a speed loop.
  2. Raise Kp (for example double it each try) until the system starts to oscillate steadily. Then back off to roughly half of that value. This gives a quick but not-yet-calm response.
  3. Add Kd from a small value upward until the overshoot and wobble are damped. Too much Kd makes the output jittery or noisy, and you will hear the motors buzz.
  4. Add a small Ki only if there is a steady error that you care about (a speed loop usually needs it; a line follower often needs little or none). Raise it slowly. If the response gets slower to settle or starts to swing, reduce it.
  5. Test on the real thing: different battery levels, the actual floor, a sharp turn. Re-tune a little if needed.

Ziegler-Nichols closed-loop method

This classic method gives you a first guess from two measurements:

  1. Set Ki = 0 and Kd = 0.
  2. Raise Kp until the output oscillates with a steady, constant amplitude. That gain is the ultimate gain, Ku.
  3. Measure the time of one full oscillation (peak to peak). That is the ultimate period, Tu, in seconds.

Then the table below gives gains. The original table is written with an integral time Ti and derivative time Td; the last two columns convert to the Ki and Kd used in our code (Ki = Kp / Ti, Kd = Kp × Td).

Example with made-up numbers: suppose the loop oscillates steadily at Ku = 40 with a period Tu = 0.4 s. The PID row gives Kp = 24, Ki = 1.2 × 40 / 0.4 = 120 and Kd = 0.075 × 40 × 0.4 = 1.2.

Treat Ziegler-Nichols as a starting point

The method is designed for a quarter-amplitude decay, which means noticeable overshoot. On a small fast robot it usually gives aggressive gains: lots of overshoot and twitchy motors. Use the numbers as a first guess, then reduce them (often Kp to about half, and Ki and Kd to match) and finish by hand. Also be careful while finding Ku: a robot oscillating at full strength can jump off the bench.

Watch your tuning with the Serial Plotter

Numbers scrolling in the Serial Monitor are almost useless for tuning. The Arduino IDE's Serial Plotter (Tools menu) draws live graphs. Print values separated by spaces or commas, one line per sample, and the plotter draws one curve for each:

// Inside the control loop, at most every 20-50 ms
Serial.print(setpoint);  Serial.print(' ');
Serial.print(measured);  Serial.print(' ');
Serial.println(output);
  • Close the Serial Monitor first, and use the same baud rate as in Serial.begin() (for example 115200).
  • Printing is slow. Do not print on every pass of a fast loop; it will disturb the very timing you are tuning.
  • A neat trick: make the setpoint toggle between two values every couple of seconds, so you get a repeating step to look at.

Practical PID: what the textbook leaves out

The equation works on paper. On a robot, a handful of practical details decide whether it works for real.

1. Use a fixed sample time

The integral and derivative both depend on dt. If the loop runs at uneven intervals, the terms are wrong. Run the controller on a timer as in Lesson 02 and compute the real elapsed time every pass:

const unsigned long LOOP_US = 10000;          // 10 ms = 100 Hz (example)
unsigned long lastLoopUs = 0;

void loop() {
  unsigned long now = micros();
  if (now - lastLoopUs < LOOP_US) return;     // not yet
  float dt = (now - lastLoopUs) / 1000000.0f; // actual elapsed seconds
  lastLoopUs = now;
  // ... measure, pidCompute(..., dt, ...), drive ...
}

2. Integral windup and anti-windup

If the motors are already at full power and still not there (a big step, a blocked wheel), the error stays large, and the integral keeps adding it up. It becomes huge. Even after the robot reaches the target, that stored sum keeps pushing it past: this is integral windup.

The simplest fix is clamping: limit how big the integral may get. That is the integralLimit parameter of pidCompute(). Choose it so that Ki × integralLimit is a modest part of your output range, for example no more than the full PWM range of 255. A second common method is to stop integrating while the final output is saturated; it needs the saturated output, so it is done in the loop that calls the controller. Also call pidReset() whenever the robot stops or the controller is switched on, so old history is forgotten.

3. Limit the output

The motors accept -255..255. Clamp the result of pidCompute() to that range before calling drive() (constrain() does it). The robot must never send a number the hardware cannot use.

4. Derivative kick

Imagine the setpoint jumps suddenly. The error jumps with it, and (e − lastError) / dt becomes enormous for one sample: a violent spike in the output called derivative kick. The cure is to take the derivative of the measurement instead of the error. When the setpoint is constant, the two are the same except for a sign (de/dt = −dy/dt), but the measurement does not jump when you change the setpoint.

// Variant: derivative on measurement. s.lastError is reused to hold the
// previous MEASUREMENT here, so use a separate PidState for this variant.
float pidComputeOnMeasurement(const PidGains& g, PidState& s, float setpoint,
                              float measurement, float dtSeconds,
                              float integralLimit) {
  if (dtSeconds <= 0) return 0;
  float error = setpoint - measurement;
  s.integral += error * dtSeconds;
  s.integral = constrain(s.integral, -integralLimit, integralLimit);
  float dMeas = (measurement - s.lastError) / dtSeconds;   // rate of the measurement
  s.lastError = measurement;
  return g.kp * error + g.ki * s.integral - g.kd * dMeas;  // minus sign
}

For a line follower the setpoint is always 0 (“line in the middle”) and never jumps, so derivative on error is fine. For a speed controller whose target changes, derivative on measurement is the better choice. Also remember to call pidReset() before the very first sample so that the first derivative is not computed from an old value.

5. Derivative noise and a simple filter

Differentiating amplifies noise. A reading that wiggles by ±5 counts turns into a huge, jumpy derivative when dt is small. Two cheap remedies: keep Kd modest, and smooth the derivative with a low-pass filter (an exponential moving average):

float dFiltered = 0;
const float D_ALPHA = 0.3f;     // 0..1: smaller = smoother but slower

// each loop, after computing 'derivative':
dFiltered = D_ALPHA * derivative + (1.0f - D_ALPHA) * dFiltered;
// then use dFiltered in place of 'derivative'

A filter adds a little delay, which works against the damping you wanted, so use as little as will do. Sometimes it is simpler to average the sensor readings first.

6. Units and scaling

Choose the units of the error and the output on purpose. A speed error in counts per second is a number in the thousands, while a PWM output only goes up to 255, so Kp will be small (like 0.02). A line position error is up to ±3500, so its Kp is small too. It is easy to be a factor of 100 off in your first guess; if the robot does almost nothing or shakes violently at the first try, check the scale first.

7. Deadband and stiction in motors

Small DC motors do not move at all below a minimum PWM (static friction plus the gearbox). A PID output of 10 might do nothing, then suddenly 40 makes the wheel jump. For a speed loop you can add a small constant push in the direction of the command:

const int MIN_PWM = 35;          // example: find yours by slowly raising PWM until the wheel just turns

int applyDeadband(float u) {
  if (u > 0.5f)  return constrain((int)u + MIN_PWM, 0, 255);
  if (u < -0.5f) return constrain((int)u - MIN_PWM, -255, 0);
  return 0;                      // really zero: stay still
}

The integral term also helps: it keeps growing until the wheel finally moves. If you see the wheel “sticking, then jumping” at low speed, stiction is the reason.

Using it: two short examples

(a) Motor speed control from the encoders

Lesson 05 showed how to measure speed: count encoder ticks during a fixed interval. Here that measurement is the measured value, and a PID loop decides the PWM. The loop below (both wheels, 20 ms period) assumes encodersBegin() and motorsBegin() were called in setup(). The speed unit is encoder counts per second; with the assumed 1400 counts per wheel turn and 34 mm wheels, 3000 counts/s is about 2.1 wheel turns per second, or roughly 230 mm/s (a mid-range, achievable value; yours will differ).

PidGains speedGains = {0.02f, 0.15f, 0.0f};         // example values only
const float I_LIMIT = 255.0f / 0.15f;               // Ki * I_LIMIT = 255 at most
PidState leftPid, rightPid;

float targetCps = 3000;                             // wanted speed, counts per second
long lastL = 0, lastR = 0;
unsigned long lastUs = 0;

void setup() {
  motorsBegin();
  encodersBegin();
  lastUs = micros();
}

void loop() {
  unsigned long now = micros();
  if (now - lastUs < 20000UL) return;               // 20 ms period
  float dt = (now - lastUs) / 1000000.0f;
  lastUs = now;

  long l = leftTicks(), r = rightTicks();
  float speedL = (l - lastL) / dt;                  // counts per second
  float speedR = (r - lastR) / dt;
  lastL = l;  lastR = r;

  float uL = pidCompute(speedGains, leftPid,  targetCps - speedL, dt, I_LIMIT);
  float uR = pidCompute(speedGains, rightPid, targetCps - speedR, dt, I_LIMIT);

  drive(constrain((int)uL, -255, 255), constrain((int)uR, -255, 255));
}
  • With a 20 ms interval, one encoder count equals 50 counts/s of speed. That coarse step is normal; do not use Kd here, or smooth the speed first.
  • If a wheel direction is reversed (counts go negative when driving forward), fix the sign in the encoder code, not in the PID.
  • Stand the robot on a box so the wheels spin freely for the first tests.

(b) Steering from the line error

For a line follower the measurement is the line position from readLinePosition() (−3500 to +3500, 0 = centred) and the goal is 0. The PID output becomes a steering correction added to one wheel and subtracted from the other. Lesson 08 builds the complete line follower, so here is only the loop:

PidGains steerGains = {0.03f, 0.0f, 0.002f};        // example values only
PidState steerPid;
const int BASE_SPEED = 120;

void followStep(float dt) {
  bool lineSeen;
  int position = readLinePosition(lineSeen);
  if (!lineSeen) { pidReset(steerPid); return; }    // handled elsewhere (Lesson 07/08)

  // Convention: positive error = line is to the right = steer right.
  float correction = pidCompute(steerGains, steerPid, (float)position, dt, 1000.0f);
  int c = constrain((int)correction, -BASE_SPEED, BASE_SPEED);

  drive(BASE_SPEED + c, BASE_SPEED - c);            // left faster = turn right
}

If the robot runs away from the line instead of towards it, the sign is wrong: swap the sign of the error (or of c). Start with only Kp, as in the tuning steps, then add Kd.

Practice tasks

  1. Print the terms: run the speed loop with the wheel in the air and plot the setpoint and measured speed in the Serial Plotter. Change only Kp and sketch what happens.
  2. Find Ku and Tu: with Ki = Kd = 0, find the steady oscillation, measure the period from the plot, and calculate the Ziegler-Nichols PID gains. Then try half of them.
  3. Windup experiment: briefly hold a wheel still while the speed loop runs with a very large I_LIMIT, then let go. Repeat with a small limit and compare.
  4. Stiction: find the lowest PWM at which each wheel turns, and use it as MIN_PWM.
  5. Dry run for Lesson 08: put the steering loop on your line follower and get it to follow a gentle curve with Kp only.

Key takeaways

  • Feedback compares what you want (setpoint) with what you measure; the error e = r − y is what the controller works on.
  • P reacts to the present error, I removes the leftover error built up from the past, and D damps by reacting to the trend.
  • Code form: u = Kp·e + Ki·∑e·dt + Kd·(e − lastE)/dt, with a steady, measured dt.
  • Too-high gains plus delay cause overshoot, oscillation and finally instability.
  • Tune by hand: Ki = Kd = 0, raise Kp to oscillation and back off, add Kd, then a little Ki if needed. Ziegler-Nichols (PID: Kp = 0.6 Ku, Ki = 1.2 Ku/Tu, Kd = 0.075 Ku Tu) is only an aggressive starting point.
  • Practical PID needs: fixed sample time, integral clamping, output limits, derivative on measurement when the setpoint changes, a filtered derivative, sensible units and a minimum PWM for stiction.
