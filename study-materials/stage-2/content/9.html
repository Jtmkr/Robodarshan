Two kinds of maze

A maze solver has to do two jobs. First it explores: it drives through the maze, finds the finish and remembers what it saw. Then it runs fast: it uses that memory to drive straight to the finish by the shortest route, skipping every dead end. This lesson teaches both jobs for the two kinds of maze the club uses.

Part A: the “2D maze”

A maze drawn as a line on the floor. The robot uses the QTR-8A line array and the encoders, and finds the shortest path with Dijkstra's algorithm.

Part B: the “3D maze”

The club's name for a maze with physical walls, like a micromouse maze. The robot cannot see a line, so it measures distances to the walls with ultrasonic sensors, then reuses the same Dijkstra function.

The five ideas from the syllabus appear in both parts: junction detection, decision making, dead ends, path recording and an introduction to shortest path. Part A teaches them in detail on the line maze; Part B shows what changes when the maze has walls.

Assumptions in this lesson
  • Robot as in the other Stage 2 lessons: ESP32, TB6612FNG, N20 motors with encoders. Assumed TICKS_PER_REV = 1400, wheel diameter 34 mm, wheel base 85 mm. Replace them with your own values.
  • Line maze: black line about 20 mm wide on a white floor, and the sensor bar sits about 40 mm in front of the wheel axle (SENSOR_AHEAD_MM). Measure your own robot.
  • Wall maze: cells 300 mm wide (clear space between walls), flat hard walls, a robot about 100 mm wide and 120 mm long. These numbers are only examples.
  • Maths uses the compass headings 0 = north, 1 = east, 2 = south, 3 = west. Forward wheel motion counts encoder ticks up.
This is starter code

The code in this lesson was written without access to the hardware. Pins, wheel directions, thresholds and speeds must be tested and tuned on your robot. The Dijkstra function and the turn conversion are plain C++ and were also checked on a computer against the worked example, but the robot parts were not run.

Part A: the line maze and junction detection

A line maze is a set of black lines that split, join and end. Each place where something interesting happens is a node: a junction, a dead end or the finish. The stretch of line between two nodes is an edge. Everything in this lesson is built from those two words.

The junction types

Look at the patterns for T and cross: at the moment the robot first sees them they are identical (every sensor dark). The array only sees a thin slice of the maze, so one look is not enough. The fix is simple: roll a short distance forward with the encoders and look again. While rolling, remember whether the outer sensors saw a branch on the left or right. At the end of the roll, check whether the line continues straight ahead.

The code

First some helpers that turn encoder ticks into millimetres. With the assumed numbers one tick is about 0.076 mm, so 1 mm is about 13 ticks.

const float MM_PER_TICK = (PI * WHEEL_DIAMETER_MM) / TICKS_PER_REV;   // about 0.0763 mm

long  mmToTicks(float mm) { return (long)(mm / MM_PER_TICK); }
float avgMm() { return (leftTicks() + rightTicks()) / 2.0f * MM_PER_TICK; }  // distance since resetEncoders()

const uint16_t DARK            = 600;    // calibrated value (0..1000) that counts as "on the line"
const float SENSOR_AHEAD_MM    = 40.0;   // ASSUMPTION: bar is this far in front of the axle
const float JUNCTION_ROLL_MM   = 50.0;   // roll until the axle is over the junction centre
const int   ROLL_SPEED = 90, TURN_SPEED = 100, BASE_SPEED = 130, FAST_SPEED = 200;  // tune these

The line follower from Lessons 05 and 06 is used as it is. Here it is wrapped in a loop that stops as soon as something other than a plain line appears under the array:

void followStep(int baseSpeed);   // ONE step of your PID line follower (Lessons 05 and 06)

// Follow the line until an outer sensor sees a branch, or the line disappears.
void followUntilEvent(int baseSpeed) {
  uint16_t cal[NUM_SENSORS];
  while (true) {
    followStep(baseSpeed);
    readCalibrated(cal);        // reads the sensors a second time; merge the two reads in your own code
    bool leftSeen  = cal[0] > DARK || cal[1] > DARK;
    bool rightSeen = cal[6] > DARK || cal[7] > DARK;
    bool anyDark = false;
    for (int i = 0; i < NUM_SENSORS; i++) if (cal[i] > DARK) anyDark = true;
    if (leftSeen || rightSeen || !anyDark) return;
  }
}

struct Seen { bool left, right, ahead, allDark; };

// Roll forward so the axle sits over the junction, and note what the array saw on the way.
Seen rollAndLook() {
  Seen s = {false, false, false, false};
  uint16_t cal[NUM_SENSORS];
  resetEncoders();
  drive(ROLL_SPEED, ROLL_SPEED);
  while (avgMm() < JUNCTION_ROLL_MM) {
    readCalibrated(cal);
    if (cal[0] > DARK || cal[1] > DARK) s.left  = true;
    if (cal[6] > DARK || cal[7] > DARK) s.right = true;
  }
  drive(0, 0);
  readCalibrated(cal);                          // look at what is under the array now
  s.ahead = (cal[3] > DARK || cal[4] > DARK);
  s.allDark = true;
  for (int i = 0; i < NUM_SENSORS; i++) if (cal[i] <= DARK) s.allDark = false;
  return s;
}
Why the roll distance matters

The robot turns around its axle, not around the sensor bar. If you turn while the bar is still 40 mm before the junction, the robot swings off the line. The roll puts the axle over the middle of the junction. Take SENSOR_AHEAD_MM plus half the line width as a starting value and adjust until your turns land on the line.

False junctions

A wobbling robot can touch the outer sensors on a sharp curve or a thick line patch. If you get ghost junctions, require the outer sensors to stay dark for two or three loops in a row, or check that the line is a different width from your normal tape.

Decision making: the left-hand rule

At each junction the robot must pick a direction. During the exploration run it uses the simplest strategy there is, the left-hand rule: always take the leftmost option. In order of priority: turn left if possible, otherwise go straight, otherwise turn right, otherwise turn around.

char decideLeftHand(const Seen& s) {
  if (s.allDark) return 'F';    // finish
  if (s.left)    return 'L';
  if (s.ahead)   return 'S';
  if (s.right)   return 'R';
  return 'U';                   // nothing at all: dead end, turn around
}

// Heading after a turn: 0 = north, 1 = east, 2 = south, 3 = west. Right = +1, left = +3, U = +2.
int headingAfter(int heading, char t) {
  int quarter = (t == 'L') ? 3 : (t == 'R') ? 1 : (t == 'U') ? 2 : 0;
  return (heading + quarter) % 4;
}

// Compare two headings and say which turn gets you from one to the other.
char turnChar(int from, int to) {
  switch ((to - from + 4) % 4) {
    case 0:  return 'S';
    case 1:  return 'R';
    case 2:  return 'U';
    default: return 'L';
  }
}

Turning with the encoders

For a spin on the spot, each wheel moves along an arc. The ticks per wheel for an angle θ are (wheel base ÷ wheel diameter) × (θ ÷ 360) × ticks per revolution. With the assumed numbers 90° is (85 ÷ 34) × 0.25 × 1400 = 875 ticks per wheel. Wheel slip makes the real angle a little different, so be ready to multiply by a correction factor.

// Spin on the spot by 'deg' degrees (positive = clockwise = right). Blocking, uses the encoders.
void spinDegrees(int deg) {
  long target = (long)(fabsf((float)deg) / 360.0f * (WHEEL_BASE_MM / WHEEL_DIAMETER_MM) * TICKS_PER_REV);
  int sgn = (deg > 0) ? 1 : -1;
  resetEncoders();
  drive(TURN_SPEED * sgn, -TURN_SPEED * sgn);   // right turn: left wheel forward, right wheel back
  while (labs(leftTicks()) < target) delay(1);
  drive(0, 0);
}

// On a line maze: spin most of the way by encoders, then creep until the line is under the middle.
void turnOnLine(char t) {
  if (t == 'S') return;
  int deg = (t == 'L') ? -90 : (t == 'R') ? 90 : 180;
  spinDegrees(deg > 0 ? deg - 30 : deg + 30);
  int sgn = (deg > 0) ? 1 : -1;
  uint16_t cal[NUM_SENSORS];
  unsigned long t0 = millis();
  drive(TURN_SPEED * sgn, -TURN_SPEED * sgn);
  do { readCalibrated(cal); }
  while (cal[3] < DARK && cal[4] < DARK && millis() - t0 < 1500);   // timeout so we never spin forever
  drive(0, 0);
}

Why it works, and when it does not

If the maze has no loops, then it is one big tree of corridors, and every wall belongs to one connected piece. Keeping your left hand on the wall, you walk along that piece all the way round and see every corridor, so you must also reach the finish. Nothing needs to be remembered.

  • Loops break the guarantee. If a loop surrounds an island, the robot can circle the island forever. A finish that sits on such an island is never reached.
  • The route it finds is not the shortest. It includes every dead end it enters.
  • It must be told where to stop. The rule does not know what a finish is; the finish patch does.

That is why the robot does not only act: it records what it sees, as the next sections show.

Dead ends

A dead end is a line that stops. For the array it looks like no line under any sensor and no branch on either side, even after the short roll. The left-hand rule has a built-in answer: nothing to the left, nothing ahead, nothing to the right, so turn around.

  1. Detect: followUntilEvent() returns because the line vanished, and rollAndLook() finds nothing.
  2. Mark: create a node of kind N_DEAD_END at the current position and store the edge that led here. Later, Dijkstra will never choose a path that ends in a dead-end node, because it is not the finish.
  3. U-turn: turnOnLine('U') spins about 150° by the encoders and then creeps until the line is back under the middle sensors.
  4. Continue: drive back along the same edge. The next node it reaches is the junction it came from.
A dead end is information

Walking into a dead end is not a failure. It costs time during exploration, but because it is recorded, the fast run knows never to go there.

Path recording

Idea 1: record the turns

The easiest memory is a list of the turn made at each junction: L, L, U, S, R, ... (U = U-turn at a dead end). Every time you see a pattern like turn, U-turn, turn, you went into a dead end and came back, so the three letters can be replaced by one. Add the angles (L = −90°, R = +90°, S = 0°, U = 180°) and convert the total back to a letter:

RecordedAngle sumBecomes
L U L−360°S
L U S+90°R
S U L+90°R
L U R+180°U
S U S+180°U

Repeating the replacement removes all the dead ends and leaves the shortest route as a short string such as L S R R. It is a lovely, tiny algorithm, and it uses almost no memory.

Why it is not enough

That trick only works for a maze without loops, where there is exactly one clean route between two points once the dead ends are gone. With loops:

  • The turn string alone cannot tell the robot it has come back to a junction it already knows, so a trip round a loop looks like a normal part of the route.
  • Removing dead ends does not choose between two different routes to the same place. You need to compare the lengths of the alternatives.

So for mazes with loops we record a graph: a list of nodes and a list of edges, each edge carrying its length measured by the encoders.

Idea 2: nodes, edges and odometry

To say “this is a junction I have seen before” the robot needs to know where it is. It keeps a position (x, y) in millimetres and a heading, updated with the encoders. In a maze whose lines run along a grid the heading is always one of four directions, so no gyro integration is needed: just keep the heading as a number and add the travelled distance along the right axis. After a turn, the heading changes by ±1 (or 2 for a U-turn).

When the robot reaches a node it asks: is there already a node within a small tolerance of this position? If yes, it is the same node, and the robot also snaps its position to the stored one. This removes all the accumulated error each time a known node is reached.

const int MAX_NODES = 64;              // 6x6 cell maze = 36 cells; a line maze rarely needs more than 32
enum NodeKind : uint8_t { N_START, N_JUNCTION, N_DEAD_END, N_FINISH };

struct Node { float x, y; uint8_t kind; };            // mm from the start, kind of node
Node     nodes[MAX_NODES];  int nodeCount = 0;
uint16_t edgeLen[MAX_NODES][MAX_NODES];                // mm, 0 = no edge        (8 KB)
int8_t   edgeDir[MAX_NODES][MAX_NODES];                // heading when leaving a toward b (4 KB)

const int   DX[4] = {0, 1, 0, -1};                     // heading 0..3 = N, E, S, W
const int   DY[4] = {1, 0, -1, 0};
const float MATCH_TOL_MM = 60;                         // must be smaller than half the shortest edge

float posX = 0, posY = 0;                              // odometry, mm
int   heading = 0, lastNode = 0;

void clearMap() {
  memset(edgeLen, 0, sizeof(edgeLen));
  nodeCount = 0;
  posX = posY = 0; heading = 0;
}

int findOrAddNode(uint8_t kind) {
  for (int i = 0; i < nodeCount; i++) {
    if (fabsf(nodes[i].x - posX) < MATCH_TOL_MM && fabsf(nodes[i].y - posY) < MATCH_TOL_MM) {
      posX = nodes[i].x;  posY = nodes[i].y;           // known node: snap, forget the drift
      return i;
    }
  }
  if (nodeCount >= MAX_NODES) return nodeCount - 1;    // out of space: keep going, but check the size
  nodes[nodeCount] = {posX, posY, kind};
  return nodeCount++;
}

void addEdge(int a, int b, uint16_t lenMm, int dirAB) {
  if (a == b || edgeLen[a][b] != 0) return;            // ignore loops onto itself and known edges
  edgeLen[a][b] = edgeLen[b][a] = lenMm;
  edgeDir[a][b] = dirAB;
  edgeDir[b][a] = (dirAB + 2) % 4;                     // going back is the opposite heading
}
An explicit grid is the other option

If the maze is built from tiles of a known size (for example every junction is a multiple of 200 mm apart), skip the tolerance test. Round the odometry to the nearest tile and use the tile number as the node number. It is simpler and safer, but only when the tile size is really known.

The exploration run

Now the whole exploration run is a short loop. The edge length is the distance driven since the last turn plus JUNCTION_ROLL_MM; using the same rule for every edge keeps the lengths consistent, which matters more than being exact to the millimetre.

char turnLog[100];  int turnLogLen = 0;                // the plain turn sequence, for debugging

void exploreLeftHand() {
  clearMap();
  lastNode = findOrAddNode(N_START);
  resetEncoders();
  while (true) {
    followUntilEvent(BASE_SPEED);
    float run = avgMm() + JUNCTION_ROLL_MM;            // length of this edge
    Seen s = rollAndLook();
    char t = decideLeftHand(s);

    posX += run * DX[heading];                         // odometry along the current heading
    posY += run * DY[heading];
    uint8_t kind = (t == 'F') ? N_FINISH : (t == 'U') ? N_DEAD_END : N_JUNCTION;
    int node = findOrAddNode(kind);                    // may snap posX/posY
    addEdge(lastNode, node, (uint16_t)run, heading);

    if (turnLogLen < 99) turnLog[turnLogLen++] = t;
    if (t == 'F') { drive(0, 0); return; }             // finish: stop exploring

    turnOnLine(t);
    heading = headingAfter(heading, t);
    lastNode = node;
    resetEncoders();
  }
}

Show the map on the Serial Monitor

A map you cannot see is a map you cannot debug. Print it after every run. Tools → Serial Monitor at 115200 baud, as in Lesson 01.

void printMap() {
  const char* KIND_NAME[] = {"START", "JUNCTION", "DEAD_END", "FINISH"};
  const char  DIR_NAME[]  = "NESW";
  Serial.println("--- nodes: id  x(mm)  y(mm)  kind ---");
  for (int i = 0; i < nodeCount; i++)
    Serial.printf("%2d  %6.0f  %6.0f  %s\n", i, nodes[i].x, nodes[i].y, KIND_NAME[nodes[i].kind]);
  Serial.println("--- edges: a  b  length(mm)  heading a->b ---");
  for (int a = 0; a < nodeCount; a++)
    for (int b = a + 1; b < nodeCount; b++)
      if (edgeLen[a][b]) Serial.printf("%2d %2d  %5u  %c\n", a, b, edgeLen[a][b], DIR_NAME[edgeDir[a][b]]);
  Serial.print("turns: "); Serial.write((const uint8_t*)turnLog, turnLogLen); Serial.println();
}

Shortest path: Dijkstra's algorithm

After exploration we have a graph with weights (the edge lengths) and want the cheapest route from the start node to the finish node. Dijkstra's algorithm does exactly this. The idea is a careful kind of greed:

  1. Give every node a distance: 0 for the start, ∞ (unknown) for all the others.
  2. Among the nodes not yet finished, take the one with the smallest distance. Its distance is now final: every other route to it must start with an edge from a node at least as far away.
  3. Relax its neighbours: if reaching a neighbour through this node is shorter than its current distance, update the neighbour's distance and remember this node as its previous node.
  4. Repeat until the finish is picked. Follow the previous links backwards from the finish to read the path.
Weights must not be negative

The “final” claim in step 2 only holds when no edge has a negative weight. Distances are never negative, so that is fine here.

A worked example

The edges (in cm) are: S–A 40, S–B 25, A–B 15, A–C 30, B–D 45, C–D 20, C–F 50, D–F 25, D–E 10. I ran Dijkstra on this graph in Python (code below). The table shows each node's distance after every round; prev is the node it was reached from.

Final prev links: A ← S, B ← S, C ← A, D ← B, E ← D, F ← D. Read backwards from F: F ← D ← B ← S, so the path is S → B → D → F with length 25 + 45 + 25 = 95 cm.

Three things are worth seeing in the table:

  • In round 2, B gives D a distance of 70. In round 4, C could reach D with 70 + 20 = 90, which is worse, so D stays at 70.
  • In round 4, C gives F a distance of 120. In round 5, D finds the better way, 70 + 25 = 95, and replaces it. That replacement is what “relax” means.
  • C and D are tied at 70. The code takes the lower index first (C); the answer does not depend on the tie.

Here is the same thing in Python, if you want to experiment on your computer before touching the robot:

names = "SABCDEF"
edges = [("S","A",40),("S","B",25),("A","B",15),("A","C",30),("B","D",45),
         ("C","D",20),("C","F",50),("D","F",25),("D","E",10)]
n = len(names); idx = {c: i for i, c in enumerate(names)}
w = [[0] * n for _ in range(n)]
for a, b, c in edges:
    w[idx[a]][idx[b]] = w[idx[b]][idx[a]] = c

INF = 10**9
dist = [INF] * n; prev = [-1] * n; done = [False] * n; dist[0] = 0
for _ in range(n):
    u = min((i for i in range(n) if not done[i]), key=lambda i: dist[i])
    done[u] = True
    for v in range(n):
        if w[u][v] and not done[v] and dist[u] + w[u][v] < dist[v]:
            dist[v] = dist[u] + w[u][v]; prev[v] = u

path = []; v = idx["F"]
while v != -1: path.append(names[v]); v = prev[v]
print(dist, path[::-1])        # [0, 40, 25, 70, 70, 80, 95]  ['S', 'B', 'D', 'F']

Dijkstra in C++ for the robot

On a microcontroller we avoid dynamic memory. With at most MAX_NODES nodes, an array of distances and a simple search for the smallest one is fast enough: the cost is about V² steps, that is a few thousand operations for 36 to 64 nodes, well under a millisecond. The function does not care where the graph is stored: it asks a small cost function for the weight of an edge (0 means no edge). That lets Part B reuse the exact same code.

const long INF_DIST = 1000000L;
typedef uint16_t (*EdgeCostFn)(int from, int to);      // returns the edge length, or 0 if there is no edge

// Returns the shortest distance, or -1 if the goal cannot be reached.
// path[] gets the node numbers from start to goal, pathLen how many.
long dijkstra(int start, int goal, int nodeCount, EdgeCostFn cost, int path[], int &pathLen) {
  long dist[MAX_NODES];  int prev[MAX_NODES];  bool done[MAX_NODES];
  for (int i = 0; i < nodeCount; i++) { dist[i] = INF_DIST; prev[i] = -1; done[i] = false; }
  dist[start] = 0;

  for (int round = 0; round < nodeCount; round++) {
    int u = -1;                                        // the closest unfinished node
    for (int i = 0; i < nodeCount; i++)
      if (!done[i] && dist[i] < INF_DIST && (u < 0 || dist[i] < dist[u])) u = i;
    if (u < 0) break;                                  // the rest cannot be reached
    done[u] = true;
    if (u == goal) break;
    for (int v = 0; v < nodeCount; v++) {              // relax every edge out of u
      uint16_t w = cost(u, v);
      if (w == 0 || done[v]) continue;
      if (dist[u] + w < dist[v]) { dist[v] = dist[u] + w; prev[v] = u; }
    }
  }
  if (dist[goal] >= INF_DIST) { pathLen = 0; return -1; }

  int tmp[MAX_NODES], n = 0;                           // walk back from the goal, then reverse
  for (int v = goal; v != -1; v = prev[v]) tmp[n++] = v;
  pathLen = n;
  for (int i = 0; i < n; i++) path[i] = tmp[n - 1 - i];
  return dist[goal];
}

uint16_t lineCost(int a, int b) { return edgeLen[a][b]; }   // cost function for the line-maze graph

For the example above (S = 0, A = 1, B = 2, C = 3, D = 4, E = 5, F = 6) a call dijkstra(0, 6, 7, lineCost, path, len) returns 95 and the path 0, 2, 4, 6.

From a node path to turn instructions

The robot cannot follow “nodes 0, 2, 4, 6”; it needs to know whether to turn left or right at each junction. We stored the heading of every edge, so a turn is just the difference between two headings. The function reuses turnChar() from the decision section.

// turns[k] = the turn to make at path[k] (k = 0 is the start). Returns how many turns.
int pathToTurns(const int path[], int len, int startHeading, char turns[]) {
  int h = startHeading, n = 0;
  for (int i = 0; i + 1 < len; i++) {
    int d = edgeDir[path[i]][path[i + 1]];             // heading we must have to leave path[i]
    turns[n++] = turnChar(h, d);
    h = d;
  }
  turns[n] = 0;
  return n;
}

Suppose the stored headings are S→B north, B→D east and D→F north, and the robot starts facing north. Then the turns are: at S, north to north = S; at B, north to east = R; at D, east to north = L. The instruction string is SRL.

The fast run

For the second run, the robot follows the line as before but ignores the left-hand rule: at every junction it simply carries out the next instruction. Dead ends are never visited, because no instruction leads there.

void runFast(const int path[], int len) {
  char turns[MAX_NODES];
  pathToTurns(path, len, 0, turns);                    // placed at the start, facing north like in the exploration
  resetEncoders();
  for (int i = 1; i < len; i++) {                      // i = the node we are driving towards
    followUntilEvent(FAST_SPEED);
    rollAndLook();                                     // centre the axle on the node
    if (i == len - 1) { drive(0, 0); return; }         // the finish
    turnOnLine(turns[i]);                              // turn for the node path[i]
    resetEncoders();
  }
}

void soloRun() {
  exploreLeftHand();
  printMap();
  int path[MAX_NODES], len;
  long d = dijkstra(0, nodeCount - 1, nodeCount, lineCost, path, len);   // the finish was added last
  Serial.printf("shortest = %ld mm over %d nodes\n", d, len);
  // wait for a button press, put the robot back on the start, then:
  runFast(path, len);
}
Going faster

The map also stores the length of every edge, so on a long straight edge the robot can run at full speed and start braking a little before the edge ends. That is the real benefit of keeping lengths. Use a high speed on long edges and a lower speed on short ones or before a turn.

Part B: the wall maze and ultrasonic sensors

The club calls this the “3D maze”: a maze with physical walls, like a micromouse maze, instead of a line painted on the floor. The robot has no line to follow, so it must sense the walls. The usual sensor is ultrasonic, and here we use the common HC-SR04-style module, with three of them: front, left and right.

How the sensor measures

The module sends a short burst of 40 kHz sound (inaudible to us). The sound travels to a wall, bounces back, and the module's second transducer hears it. The module sets the ECHO pin HIGH from the moment it sends the burst until the echo comes back, so the HIGH time is the round-trip time.

The sound goes there and back, so the distance is half of speed × time:

d = v × t / 2, with v ≈ 343 m/s at 20 °C. In practical units, d (cm) ≈ t (µs) / 58.

Sound is a little faster in warm air (about 0.6 m/s more per °C), which changes the answer by about 2% for a 10 °C difference. For a maze that is small enough to ignore.

What can go wrong

  • Range. Typical datasheets for the HC-SR04 give about 2 cm to 400 cm. Check your own module. In a maze you only care about the first metre.
  • Blind zone. Closer than about 2 cm the readings are wrong. Mount the sensors so a wall is never that close.
  • Beam width. The beam is a cone of roughly 15°, not a thin line. A wall corner or a side wall can return an echo that you did not expect.
  • Angled walls. A smooth wall at a steep angle reflects the ping away from the sensor like a mirror, so you get a long distance or no echo at all.
  • Soft surfaces such as foam, cloth or thin card absorb or scatter the sound and give weak or missing echoes. Use hard, flat walls.
  • Cross-talk. One sensor's ping can reach another sensor. Fire them one at a time.
Hardware warning: 5 V ECHO into a 3.3 V ESP32

A standard HC-SR04 is a 5 V module, and its ECHO output swings to 5 V. ESP32 pins are 3.3 V only, so connecting ECHO directly can damage the pin over time. Do one of these:

  • Put a voltage divider on each ECHO wire: 1 kΩ from ECHO to the ESP32 pin and 2 kΩ from that pin to GND. That gives about 3.3 V.
  • Or use a level-shifter board.
  • Or buy a 3.3 V-compatible variant (sold as HC-SR04P or similar). Read the seller's datasheet; names are not always reliable.

The TRIG input normally accepts the 3.3 V signal from the ESP32, but check yours. Power the module from a clean 5 V supply and connect all grounds together.

Non-blocking measurement

The simple Arduino way to read an HC-SR04 is pulseIn(). It waits until the echo is finished, up to its timeout. For a wall 1 m away that is about 6 ms, and with three sensors the robot would be blind to everything else for tens of milliseconds. Instead, we let a pin interrupt note the time of the rising and falling edge of ECHO with micros(), and a small function, called from loop(), fires the sensors one after another.

Suggested pins for the wall robot (the line robot does not need them): TRIG 18, 19, 23 and ECHO 16, 17, 14 (through the dividers) for front, left and right. Note that these ECHO pins are the same ones the line-follower build uses for buttons.

enum { FRONT = 0, LEFT = 1, RIGHT = 2 };
const float    MAX_CM     = 130.0;     // report this when there is no echo (about the 8 ms timeout)
const uint32_t TIMEOUT_US = 8000;      // give up on an echo after 8 ms
const uint32_t GAP_US     = 12000;     // quiet time between two sensors

struct Sonar {
  uint8_t trigPin, echoPin;
  volatile uint32_t riseUs, widthUs;
  volatile bool armed, done;
};
Sonar sonar[3] = {
  {18, 16, 0, 0, false, false},        // front
  {19, 17, 0, 0, false, false},        // left
  {23, 14, 0, 0, false, false},        // right
};
float sonarCm[3] = {MAX_CM, MAX_CM, MAX_CM};          // newest filtered distance in cm
float hist[3][3];                                      // last three raw readings per sensor

// Runs on every rising and falling edge of an ECHO pin.
void IRAM_ATTR echoIsr(void* arg) {
  Sonar* s = (Sonar*)arg;
  if (!s->armed) return;                               // ignore late echoes of an old ping
  if (digitalRead(s->echoPin)) {
    s->riseUs = micros();
  } else {
    s->widthUs = micros() - s->riseUs;
    s->done = true;
    s->armed = false;
  }
}

void sonarBegin() {
  for (int i = 0; i < 3; i++) {
    pinMode(sonar[i].trigPin, OUTPUT);
    digitalWrite(sonar[i].trigPin, LOW);
    pinMode(sonar[i].echoPin, INPUT);
    attachInterruptArg(digitalPinToInterrupt(sonar[i].echoPin), echoIsr, &sonar[i], CHANGE);
    for (int k = 0; k < 3; k++) hist[i][k] = MAX_CM;
  }
}

float median3(float a, float b, float c) {             // median of three: throws away one wild reading
  if (a > b) { float t = a; a = b; b = t; }            // now a <= b
  if (b > c) b = c;                                    // b = min(b, c)
  return (a > b) ? a : b;                              // median = max(a, min(b, c))
}

void pushReading(int i, float cm) {
  hist[i][2] = hist[i][1];  hist[i][1] = hist[i][0];  hist[i][0] = cm;
  sonarCm[i] = median3(hist[i][0], hist[i][1], hist[i][2]);
}

// Call this as often as you can from loop(). It never waits.
void sonarUpdate() {
  static uint8_t cur = 0;                              // which sensor is next
  static bool waiting = false;
  static uint32_t t0 = 0;
  uint32_t now = micros();
  Sonar& s = sonar[cur];

  if (!waiting) {
    if (now - t0 < GAP_US) return;                     // let the old echoes die away
    s.done = false;  s.armed = true;
    digitalWrite(s.trigPin, HIGH);
    delayMicroseconds(10);                             // the 10 us trigger pulse
    digitalWrite(s.trigPin, LOW);
    t0 = micros();
    waiting = true;
    return;
  }
  if (s.done || now - t0 > TIMEOUT_US) {
    float cm = MAX_CM;                                 // no echo means "nothing near"
    if (s.done) { cm = s.widthUs / 58.3f; if (cm > MAX_CM) cm = MAX_CM; }
    s.armed = false;
    pushReading(cur, cm);
    waiting = false;
    cur = (cur + 1) % 3;
    t0 = micros();
  }
}

With these settings a full round of the three sensors takes roughly 40 to 60 ms (an estimate; measure it with micros()), so each sensor gives a new reading about 15 to 25 times a second. The median of three adds about one reading of delay, which is fine at maze speeds.

Print before you trust

Before any driving, print sonarCm[FRONT], sonarCm[LEFT] and sonarCm[RIGHT] and hold a book in front of each. Check a few distances with a ruler. Check what happens at a very angled wall.

Wall following, openings and turns

Keeping a distance from the wall

This is the same idea as the line follower in Lessons 05 and 06. There the error was the line position; here it is the distance to the wall. The proportional controller turns it into a steering correction: correction = Kp × error, added to one wheel and subtracted from the other.

const float TARGET_CM = 10.0;     // ASSUMPTION: centred in a 300 mm corridor with a 100 mm wide robot
const float KP_WALL   = 8.0;      // PWM counts per cm of error: tune it
const int   WALL_SPEED = 120;

// errCm > 0 means "steer left". For the left wall that is (distance - target); for the right wall (target - distance).
void steer(float errCm) {
  errCm = constrain(errCm, -6.0f, 6.0f);                 // clamp, so a sudden gap never causes a big swerve
  int corr = (int)(KP_WALL * errCm);
  drive(WALL_SPEED - corr, WALL_SPEED + corr);
}

If the robot wobbles from side to side, lower Kp, or add a derivative term with pidCompute() from Lesson 06.

Openings are junctions

A wall maze is full of junctions, but there is no pattern to detect: a junction is simply a place where a wall stops existing. In the sensor data it looks like a jump:

  • The side distance jumps from about 10 cm to 40 cm or more: an opening on that side.
  • The front distance falls below about 18 cm: a wall ahead.

Use fixed thresholds, one for a “wall present” test, in the middle between the two cases:

const float SIDE_WALL_CM  = 20.0;   // a side reading below this = wall present
const float FRONT_WALL_CM = 18.0;   // a front reading below this = wall ahead (about 9 cm at cell centre)
const float CELL_MM       = 300.0;  // ASSUMPTION: centre of one cell to the centre of the next

// Move forward one cell using the encoders for distance and the walls for steering.
void moveOneCell() {
  resetEncoders();
  long target = mmToTicks(CELL_MM);
  while ((leftTicks() + rightTicks()) / 2 < target) {
    sonarUpdate();
    if (sonarCm[FRONT] < 7.0) break;                                  // wall much closer than expected: stop
    if      (sonarCm[LEFT]  < SIDE_WALL_CM) steer(sonarCm[LEFT] - TARGET_CM);       // follow the left wall
    else if (sonarCm[RIGHT] < SIDE_WALL_CM) steer(TARGET_CM - sonarCm[RIGHT]);     // otherwise the right wall
    else drive(WALL_SPEED, WALL_SPEED);                                // no wall at all: go straight
  }
  drive(0, 0);
}

// After a spin the sensors point somewhere new, so let the filters refill.
void settleSonar(unsigned long ms) {
  unsigned long t0 = millis();
  while (millis() - t0 < ms) sonarUpdate();
}

This uses mmToTicks() from Part A and the same encoder idea as the line maze: the encoders decide how far to go, the walls decide how to steer. The distance of one cell is not measured by the walls, so a robot that slips a little still ends in about the right place.

Front walls and turns

At the middle of each cell the robot stops and looks. spinDegrees() from Part A turns it by the encoders. You can improve the angle accuracy with the gyro in the MPU6050, but encoders are enough to start with.

The wall-follower rule

The exploration rule is the same left-hand rule as Part A, now in terms of walls: left open → turn left; otherwise front open → go straight; otherwise right open → turn right; otherwise turn around. The robot keeps its map as it goes, so it can plan the second run.

Mapping the wall maze and running fast

A grid of cells with walls

A micromouse-style maze is a grid. Each cell has up to four walls. A single byte per cell is enough: bit 0 = north wall, bit 1 = east, bit 2 = south, bit 3 = west, which is 1 << heading with the same heading numbers as before. We also need a visited flag, so the planner never trusts a cell the robot has not seen.

const int W = 6, H = 6;                                // 36 cells (fits in MAX_NODES = 64)
uint8_t wallsOf[H][W];                                 // bit (1 << direction) set = wall on that side
bool    visited[H][W];
int row = H - 1, col = 0, wallHeading = 0;             // start in the bottom-left cell, facing north (row 0 = north edge)

// Remember a wall on side 'dir' of cell (r, c), and the matching side of the neighbour.
void setWall(int r, int c, int dir) {
  wallsOf[r][c] |= 1 << dir;
  int nr = r + (dir == 2) - (dir == 0);
  int nc = c + (dir == 1) - (dir == 3);
  if (nr >= 0 && nr < H && nc >= 0 && nc < W) wallsOf[nr][nc] |= 1 << ((dir + 2) % 4);
}

void exploreWallMaze(int goalRow, int goalCol) {
  memset(wallsOf, 0, sizeof(wallsOf));  memset(visited, 0, sizeof(visited));
  while (true) {
    settleSonar(250);
    bool f = sonarCm[FRONT] < FRONT_WALL_CM;
    bool l = sonarCm[LEFT]  < SIDE_WALL_CM;
    bool r = sonarCm[RIGHT] < SIDE_WALL_CM;
    visited[row][col] = true;
    if (f) setWall(row, col, wallHeading);                // sensors give walls relative to the robot,
    if (l) setWall(row, col, (wallHeading + 3) % 4);      // so convert to compass directions
    if (r) setWall(row, col, (wallHeading + 1) % 4);
    if (row == goalRow && col == goalCol) break;

    char t = !l ? 'L' : !f ? 'S' : !r ? 'R' : 'U';        // the left-wall rule
    if      (t == 'L') spinDegrees(-90);
    else if (t == 'R') spinDegrees(90);
    else if (t == 'U') spinDegrees(180);
    wallHeading = headingAfter(wallHeading, t);
    moveOneCell();
    row += (wallHeading == 2) - (wallHeading == 0);
    col += (wallHeading == 1) - (wallHeading == 3);
  }
  drive(0, 0);
}

Here we assume the goal cell is known (for example an exit cell given in the rules). Remember the limits from Part A: a wall follower is not guaranteed to reach a goal that sits in the middle of the maze, because that goal may be on an island of walls.

Reusing Dijkstra on the cell graph

The cells form a graph: every cell is a node, and two neighbouring cells are connected by an edge if there is no wall between them. Every move costs 1 (or CELL_MM if you prefer distances; for equal cells the answer is the same path). We do not write a new algorithm. We write a different cost function and call the same dijkstra() from Part A.

// Cost 1 between two neighbouring, visited cells without a wall between them, otherwise 0 (no edge).
uint16_t cellCost(int a, int b) {
  int ar = a / W, ac = a % W, br = b / W, bc = b % W;
  if (!visited[ar][ac] || !visited[br][bc]) return 0;
  int dir;
  if      (br == ar - 1 && bc == ac) dir = 0;          // north
  else if (br == ar && bc == ac + 1) dir = 1;          // east
  else if (br == ar + 1 && bc == ac) dir = 2;          // south
  else if (br == ar && bc == ac - 1) dir = 3;          // west
  else return 0;                                       // not neighbours
  return (wallsOf[ar][ac] & (1 << dir)) ? 0 : 1;
}

int headingBetween(int a, int b) {                     // compass heading for a move between neighbouring cells
  int d = b - a;
  return (d == -W) ? 0 : (d == 1) ? 1 : (d == W) ? 2 : 3;
}

void runWallMazeFast(int startRow, int startCol, int goalRow, int goalCol) {
  int path[MAX_NODES], len;
  long steps = dijkstra(startRow * W + startCol, goalRow * W + goalCol, W * H, cellCost, path, len);
  if (steps < 0) { Serial.println("no route in the map"); return; }
  Serial.printf("shortest route: %ld cells\n", steps);

  int h = 0;                                           // robot is back at the start, facing north
  for (int i = 0; i + 1 < len; i++) {
    int d = headingBetween(path[i], path[i + 1]);
    char t = turnChar(h, d);                           // same helper as the line maze
    if      (t == 'L') spinDegrees(-90);
    else if (t == 'R') spinDegrees(90);
    else if (t == 'U') spinDegrees(180);
    h = d;
    moveOneCell();
  }
}

Notice that Dijkstra, turnChar() and headingAfter() are the same functions in both kinds of maze. Only the map and the way it is filled are different. For speed, merge consecutive straight moves into one long move, so the robot does not stop in every cell.

The next step: flood-fill

Flood-fill is the algorithm micromouse robots use. Each cell stores its distance to the goal, and when the robot discovers a new wall it updates the distances and re-plans on the spot, so it explores only what it needs and heads for the goal from the start. It uses ideas you have already met (a grid, a distance, a plan). Look it up once you can run the wall maze reliably.

Practice tasks

  1. Dijkstra on paper. Change the weight of C–F in the worked example from 50 to 40, and the weight of D–F to 60. Redo the table by hand. Which path wins now? Check with the Python code.
  2. Print the map. Without driving, fill the arrays by hand with addEdge() for a small maze and call printMap().
  3. Turn calibration. Command spinDegrees(90) four times. Measure how far off 360° the robot is, and correct the formula with a factor.
  4. Junction logger. Drive a line maze by hand and print the Seen flags at every junction. Are T and cross separated correctly?
  5. Sensor test. Check that sonarCm[] tracks a flat book at 5, 10, 20 and 40 cm. Then tilt the book 45° and see what happens.
  6. Loop challenge. Make a line maze with a loop. Does the left-hand rule still finish? Add a way to stop if the robot has visited the same node more than three times.

Key takeaways

  • A maze solver explores first and runs fast second. The map is what makes the fast run possible.
  • A line maze has nodes (junctions, dead ends, finish) and edges. Confirm a junction by rolling a short distance forward with the encoders, because T and cross look the same at first.
  • The left-hand rule works for mazes without loops, but it is not guaranteed with loops, and it does not find the shortest route.
  • Turn-sequence simplification (such as L U L becomes S) only works without loops. With loops, record a graph: node positions from odometry, edge lengths from the encoders, and snap to a known node when the position matches within a tolerance.
  • Dijkstra's algorithm picks the closest unfinished node, relaxes its neighbours and repeats; with arrays it costs about V² steps and needs no dynamic memory.
  • Convert the node path to turns by comparing the stored headings, then follow the instructions on the fast run.
  • An ultrasonic sensor measures time of flight: d = v × t / 2. It has a blind zone, a wide beam, and problems with soft and angled walls.
  • An HC-SR04's ECHO pin is 5 V: divide it down or use a 3.3 V variant for the ESP32. Read sensors without blocking, one at a time, and filter with a median of three.
  • Wall following is the line follower again, with the wall distance as the error. A vanishing side wall is a junction.
  • The wall maze reuses the same Dijkstra with a different cost function. Flood-fill is the natural next step.
