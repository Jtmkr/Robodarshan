From simple sketches to robot programs

In Stage 1 your programs did one thing at a time: read, decide, act, delay(), repeat. That is fine for blinking an LED. A real robot has to do several things at once: read eight sensors, run a controller, count wheel turns, listen to a phone and stop immediately when something goes wrong. The tools in this lesson let one ESP32 do all that without getting confused.

Arrays

Handle many sensors or values with one name and a loop.

Structures

Split the program into small, reusable pieces.

Do things on a schedule without freezing the program.

Arrays: many values, one name

A line-following robot reads several sensors. Instead of sensor1, sensor2, sensor3… you store them in an array and use a loop.

const int NUM_SENSORS = 5;
const int sensorPins[NUM_SENSORS] = {36, 39, 34, 35, 32};   // example ADC1 pins
int sensorValues[NUM_SENSORS];

void readSensors() {
  for (int i = 0; i < NUM_SENSORS; i++) {
    sensorValues[i] = analogRead(sensorPins[i]);
  }
}

void printSensors() {
  for (int i = 0; i < NUM_SENSORS; i++) {
    Serial.print(sensorValues[i]);
    Serial.print(' ');
  }
  Serial.println();
}
  • Indexes start at 0. An array of 5 has indexes 0 to 4.
  • C++ does not check the index. Writing to sensorValues[5] overwrites some other variable and causes strange bugs or crashes.
  • The size of an array is fixed when you write it. Keep it in one constant (NUM_SENSORS) and use that constant everywhere.
  • const arrays cannot be changed, which protects things like pin lists.

An array in action: where is the line?

Give each sensor a weight by position (for example −2, −1, 0, 1, 2 from left to right) and compute a weighted average of the readings. The result tells you where the line is under the robot: negative means left, zero means centred, positive means right. This number is exactly what the PID line follower uses later.

const int weights[NUM_SENSORS] = {-2, -1, 0, 1, 2};

// Returns -2.0 (line far left) ... +2.0 (line far right).
// Assumes a bigger reading means "darker line" (check your own sensor!).
float linePosition() {
  long weightedSum = 0;
  long total = 0;
  for (int i = 0; i < NUM_SENSORS; i++) {
    weightedSum += (long)sensorValues[i] * weights[i];
    total += sensorValues[i];
  }
  if (total == 0) return 0;               // no line seen at all
  return (float)weightedSum / total;
}
Count the elements automatically

sizeof(arr) / sizeof(arr[0]) gives the number of elements in an array, so you do not have to count by hand if you ever change the list.

Structures: bundle related data

A robot has two motors, and each needs the same set of pins. Writing leftIn1, leftIn2, leftPwm, rightIn1… quickly becomes a mess. A structure (struct) groups related values into one new type.

struct Motor {
  int in1;
  int in2;
  int pwmPin;
  int channel;        // PWM channel (used by ESP32 core 2.x)
};

Motor leftMotor  = {26, 27, 25, 0};
Motor rightMotor = {32, 33, 13, 1};

void setMotor(const Motor& m, int speed) {   // & = use the original, do not copy
  speed = constrain(speed, -255, 255);
  digitalWrite(m.in1, speed > 0);
  digitalWrite(m.in2, speed < 0);
  // ... write abs(speed) to m.pwmPin here, as in the previous lesson
}

void drive(int left, int right) {
  setMotor(leftMotor, left);
  setMotor(rightMotor, right);
}

Now setMotor() works for either motor, and adding a third motor means adding one line. Access a member with a dot: leftMotor.pwmPin.

Structures are useful for settings too. A PID controller needs three numbers, and keeping them together makes it easy to keep several sets of tuned values:

struct PidGains {
  float kp;
  float ki;
  float kd;
};

PidGains lineFollow = {1.2, 0.0, 0.8};     // example values only
PidGains speedControl = {0.5, 0.1, 0.0};

Modular programming: small pieces, clear jobs

When everything lives in one long loop(), changing one thing breaks another. Modular programming means splitting your code into pieces where each one has a single job and a clear name:

  • readSensors() only reads sensors.
  • linePosition() only turns readings into a position.
  • drive(left, right) only moves the motors.

Then loop() reads like a story:

void loop() {
  readSensors();
  float position = linePosition();
  int correction = computeSteering(position);
  drive(baseSpeed + correction, baseSpeed - correction);
}

Splitting into files

In the Arduino IDE you can move related functions into their own files. Use the small arrow next to the sketch tab and choose New Tab. A common pattern is a .h file that declares what a module offers and a .cpp file that implements it:

my_robot/
  my_robot.ino      the main sketch: setup() and loop()
  motors.h          what the motor module offers
  motors.cpp        how it does it
// motors.h
#pragma once                       // include this file only once

void motorsBegin();
void drive(int left, int right);   // -255 to 255 for each side
// motors.cpp
#include <Arduino.h>
#include "motors.h"

static const int AIN1 = 26;        // "static" keeps these private to this file
// ... other pins ...

void motorsBegin() {
  pinMode(AIN1, OUTPUT);
  // ... set up the other pins and PWM ...
}

void drive(int left, int right) {
  // ... set both motors ...
}
// my_robot.ino
#include "motors.h"

void setup() {
  motorsBegin();
}

void loop() {
  drive(150, 150);
}
Why bother?

You can test a module on its own, reuse it in your next robot, and share work with teammates: one person writes motors, another writes sensors. Aim for functions that do one job, are short enough to read at a glance, and have names that say what they do.

millis(): timing without freezing

delay(1000) stops your whole program for a second. During that second the robot cannot read sensors, cannot react to an obstacle and cannot answer the phone. For anything that needs to stay responsive, use millis() instead.

millis() returns the number of milliseconds since the ESP32 started. The pattern is: remember when you last did something, and do it again only when enough time has passed.

const int LED_PIN = 2;
unsigned long lastBlink = 0;
const unsigned long BLINK_INTERVAL = 500;   // ms
bool ledOn = false;

void setup() {
  pinMode(LED_PIN, OUTPUT);
}

void loop() {
  unsigned long now = millis();

  if (now - lastBlink >= BLINK_INTERVAL) {
    lastBlink = now;                        // restart the timer
    ledOn = !ledOn;
    digitalWrite(LED_PIN, ledOn);
  }

  // Everything else keeps running on every pass of loop()
}

You can run as many of these timers as you like, each with its own last... variable. A very common use is a fixed-rate control loop for your robot's controller:

const unsigned long CONTROL_PERIOD = 5;     // run the controller every 5 ms
unsigned long lastControl = 0;

void loop() {
  unsigned long now = millis();
  if (now - lastControl >= CONTROL_PERIOD) {
    lastControl = now;
    readSensors();
    // ... compute and apply the correction ...
  }
}
  • Always declare time variables as unsigned long.
  • Write the check as now - last >= interval. Subtracting like this keeps working even when millis() wraps back to zero after about 49 days. Do not write now >= last + interval.
  • For timing in microseconds (for example measuring an ultrasonic echo), use micros().

Interrupts: react the instant it happens

If you check a button or an encoder only once per loop(), you can miss fast events. A wheel encoder can produce thousands of pulses per second, far faster than a busy loop can poll. An interrupt tells the processor: “the moment this pin changes, pause what you are doing, run this small function, then go back.”

const int ENC_PIN = 34;                      // encoder signal
volatile long encoderCount = 0;              // shared with the interrupt, so volatile
portMUX_TYPE mux = portMUX_INITIALIZER_UNLOCKED;

void IRAM_ATTR onEncoderPulse() {            // the interrupt service routine (ISR)
  portENTER_CRITICAL_ISR(&mux);
  encoderCount++;
  portEXIT_CRITICAL_ISR(&mux);
}

long readEncoder() {                         // safe way to read it in loop()
  portENTER_CRITICAL(&mux);
  long count = encoderCount;
  portEXIT_CRITICAL(&mux);
  return count;
}

void setup() {
  Serial.begin(115200);
  pinMode(ENC_PIN, INPUT);
  attachInterrupt(digitalPinToInterrupt(ENC_PIN), onEncoderPulse, RISING);
}

void loop() {
  Serial.println(readEncoder());
  delay(200);
}

The same idea works for a start button. The ISR only sets a flag, and loop() does the real work:

const int BUTTON_PIN = 14;
volatile bool buttonPressed = false;
volatile unsigned long lastPress = 0;

void IRAM_ATTR onButton() {
  unsigned long now = millis();
  if (now - lastPress > 50) {                // ignore contact bounce
    buttonPressed = true;
    lastPress = now;
  }
}

void setup() {
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  attachInterrupt(digitalPinToInterrupt(BUTTON_PIN), onButton, FALLING);
}

void loop() {
  if (buttonPressed) {
    buttonPressed = false;
    // start the robot...
  }
}
Rules for interrupt functions
  • Keep them very short. Set a flag or add to a counter, nothing more.
  • Never use delay(), Serial.print() or Wi-Fi calls inside an ISR.
  • Mark the function with IRAM_ATTR on the ESP32, so it is stored where it can run instantly.
  • Any variable shared between an ISR and the rest of the program must be volatile.
  • Pins GPIO34 to GPIO39 are input-only and have no internal pull-up, so add an external resistor if you need one.

State machines: one behaviour at a time

As robots get smarter, if statements pile up and nobody can tell what the robot is supposed to do. A state machine fixes this. The robot is always in exactly one state (a mode of behaviour), and clear rules say when it moves to another state.

Before writing code, draw the states and arrows on paper like this. In code, an enum names the states and a switch runs the right behaviour:

enum State { IDLE, FOLLOW, LOST, STOP };
State state = IDLE;
unsigned long stateStart = 0;

void changeState(State next) {
  state = next;
  stateStart = millis();                      // remember when we entered it
}

void loop() {
  readSensors();

  switch (state) {
    case IDLE:
      drive(0, 0);
      if (buttonPressed) {
        buttonPressed = false;
        changeState(FOLLOW);
      }
      break;

    case FOLLOW:
      followLine();                           // the controller from a later lesson
      if (lineLost()) changeState(LOST);
      break;

    case LOST:
      searchForLine();                        // for example spin slowly
      if (!lineLost()) changeState(FOLLOW);
      else if (millis() - stateStart > 1000) changeState(STOP);   // lost for 1 s
      break;

    case STOP:
      drive(0, 0);
      break;
  }
}

Functions like followLine(), lineLost() and searchForLine() are placeholders for you to write using what you have learned. Notice how millis() and the state machine work together: stateStart lets a state know how long it has been active, with no delay() anywhere.

Good habits
  • Give each state one behaviour and a name that says it.
  • Put all the “when do we change state?” rules in one place, close to the state's code.
  • Print the state name to Serial when it changes. It makes debugging much easier.

Practice tasks

  1. Sensor array: store 5 sensor readings in an array and print the index of the largest value. Move your hand over the sensors and watch it change.
  2. Struct: create a Motor struct and a setMotor() function. Make both motors run forward for 2 seconds, then stop, without delay().
  3. Two timers: blink an LED every 500 ms and print a message every 2 seconds, using only millis().
  4. Interrupt: attach a button interrupt that toggles a flag, and print “pressed” from loop(). Check that one press counts once.
  5. State machine: make an LED with three states (off, slow blink, fast blink). Each button press moves to the next state.

Common mistakes

  • Using delay() inside loop() for anything that must stay responsive.
  • Forgetting volatile on a variable that an interrupt changes.
  • Printing to Serial or waiting inside an interrupt function.
  • Going past the end of an array (for example <= instead of < in a for loop).
  • Using int for time values. Use unsigned long.

Key takeaways

  • Arrays and loops let you treat many sensors as one group. Mind the index range.
  • Structures bundle related data, so one function can serve every motor.
  • Modular code gives each function a single job and lets loop() read like a story.
  • millis() replaces delay(): remember when you last acted and check now - last >= interval.
  • Interrupts catch fast events. Keep the ISR tiny, use volatile and IRAM_ATTR.
  • A state machine keeps complex robot behaviour organised: one state, one behaviour, clear transitions.
